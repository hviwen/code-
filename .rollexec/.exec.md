## 2. 来源权重与选题策略
- 对每日的“JS、CSS、HTML、前端框架、工程化、Git”题目，书签参考库必须构成 65%–80% 的主要参考依据。按当天主题选取最相关的 3–8 个书签，而非机械平均使用全部链接。

- 书签内容是候选资料，不是权威结论。若与规范、当前主流实践、官方文档或近期工程事实冲突，以一手资料和可验证实践为准，并在审校中标注“已修正”。
- 选题要覆盖“基础复习 + 高频提问 + 项目实战深挖”，每日任务量适合 90–150 分钟完成，避免把内容堆成资料仓库。

## 3. 专家审校与题目准入
以资深前端专家的身份审校每个候选问题和答案，再落库。禁止把未经审查的抓取内容直接写入题库。
逐项评价：
1. 时效性：是否使用过时 API、已废弃工具、旧浏览器限制或不再推荐的实践；标注 current、needs-update 或 deprecated。
2. 提问质量：问题边界是否清楚，是否能考察真实能力，是否避免纯记忆式、诱导式或含糊提问。
3. 技术正确性：答案是否符合 JavaScript/HTML/CSS/浏览器规范、框架官方语义和工程事实。
4. 严谨性与完整性：是否说明前提、边界、反例、权衡、错误处理、性能与安全影响。
5. 最优性与实战性：是否给出当前合理方案及其替代方案，是否能映射至真实前端项目。
6. 证据强度：来源分级为 primary（官方规范/官方文档）、curated（书签高质量资料）、community（GitHub/社区）或 local（用户项目/笔记）。
每题生成 verdict（approved、revised、hold、deprecated）与简短审校结论；只有 approved 和 revised 的题目才进入可训练题库。hold/deprecated 保留在审校记录，不能进入每日训练清单。发现资料陈旧或答案不完整时，写出“原问题/原结论问题点、修订后的提问、修订后的答案、采用依据”。

## 4. Obsidian 目录与数据模型
在 Vault 内创建和维护以下目录，保留用户内容，不覆盖同名笔记：
AI Knowledge Factory/
- Daily/YYYY-MM-DD.md：当天入口与训练计划
- Interview Questions/：已准入的 JS、CSS、HTML、前端、框架、工程化、Git 等题目
- LeetCode/：算法题与 TypeScript 解题记录
- Project Deep Dives/：项目建设与架构深挖
- AI Tools/：AI 工具与工作流训练
- Review Plans/：间隔复习计划
- Source Registry/Bookmarked Sources.md：书签来源清单、分类、最后使用时间、可靠性备注
- Quality Reviews/YYYY-MM-DD.md：当天候选题的审校记录与淘汰理由
- Dashboard.md：总览看板
- Data/question-index.md：题目索引与统计明细

每个“题库类”笔记应有 Obsidian frontmatter：
- type: interview-question | leetcode | project-deep-dive | ai-tool
- topic、subtopic、difficulty（basic | intermediate | advanced）
- source_tier、source_urls、source_mix（bookmark | local | github | primary 的百分比）
- review_status、reviewed_at、freshness
- knowledge_id、created、last_review、next_review
- tags
使用稳定的 knowledge_id，采用中文标题与必要的英文术语，建立 wikilinks。引用使用 References 区，附 URL 与来源等级。

## 5. 每日输出
Daily/YYYY-MM-DD.md 必须包括：
- 今日目标、预计总时长、优先级
- 本地笔记与 Git 改动摘要
- 本日采用书签及其占比（应在 65%–80%，不适用时说明例外）
- GitHub 热点摘要与链接
- 基础复习：3–5 个基础知识卡片，覆盖定义、机制、边界与常见误解
- 高频面试题：8–15 道，从 JS、CSS、HTML、浏览器、前端框架、工程化、Git 中按主题分配；每题包含提问、考察意图、标准答案、边界/取舍、常见误区、追问、来源与审校 verdict
- LeetCode：2–4 题，初级 1–2 题、中级 1–2 题；每题需有题号、标题、难度、考点、思路、时间/空间复杂度、TypeScript 参考实现、至少两个测试、常见错误和前端业务迁移场景。14 天内不得无理由重复同题
- 项目建设深挖：2–3 项，绑定 Git 变化或明确业务场景，覆盖需求拆解、模块边界、状态管理、数据获取与缓存、鉴权、异常处理、性能、可观测性、测试、CI/CD、发布回滚、跨端、可维护性、选型和协作中的至少两项。每项有面试题、优秀回答框架、关键取舍、风险、落地改进、追问
- AI 工具训练：2–3 项，结合前端/React Native/uni-app 工作流，覆盖需求分析、代码生成、审查、调试、测试、重构、文档、上下文与提示词、MCP/Agent、隐私安全、模型选择/成本、验证。每项说明输入上下文、操作步骤或提示模板、如何人工验证输出、失败模式和面试回答角度；强调 AI 输出必须经人工审查、测试和安全检查
- 间隔复习：今日、+1、+3、+7、+14、+30 天的待复习项
- 运行备注：来源失败、时效风险、待人工确认项。

## 6. 总览看板与索引
每次运行后更新 AI Knowledge Factory/Dashboard.md 和 Data/question-index.md，生成无需第三方插件即可阅读的 Markdown 看板。Dashboard.md 至少包括：
- 总题量及本次新增量，按 type 分类：基础复习、面试题、LeetCode、项目深挖、AI 工具
- 按 topic 分类：JS、TS、HTML、CSS、浏览器、React、Vue、Node、Git、工程化、性能、跨端、算法、AI 工具
- 难度分布：basic / intermediate / advanced
- 审校状态：approved / revised / hold / deprecated
- 资料来源分布：bookmark / local / github / primary；展示书签参考占比与近 7 天均值
- 复习状态：到期、逾期、未来 7 天
- 最近 7 天主题覆盖和缺口：连续 7 天未覆盖的高优主题须列为“下次推荐”
- 近期来源质量告警：过时、互相矛盾、无一手依据的内容
使用简洁表格、可点击的 wikilinks 和日期；不要使用图像或依赖 Dataview。Data/question-index.md 维护一行一个知识条目的可检索索引，含 knowledge_id、类型、主题、难度、状态、来源、创建日期、下次复习链接。

## 7. 推荐的持续改进
- 每周一次，在周日的 Daily 文件增加“周度质量回顾”：主题覆盖、重复率、复习完成率、书签使用率、被判定陈旧的题目数、下周缺口与 3 个优先主题。
- 对在近 30 天多次答错或复习逾期的知识点提高出现优先级；对连续正确且有项目迁移案例的知识点降低频率。
- 建立“题目变更日志”：当同一 knowledge_id 的结论因规范或框架版本更新而改变时，保留修订理由、日期和来源，避免旧答案悄然覆盖。
- 每月抽样复核至少 10% 的 approved/revised 题目，优先复核高频、高影响或依赖社区来源的条目。
