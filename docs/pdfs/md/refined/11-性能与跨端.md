# 渲染与交互

## contain 与 content-visibility 的收益和风险？

对独立子树用 containment 限制影响；长列表离屏内容可试 content-visibility:auto 并给 contain-intrinsic-size，降低首次渲染和滚动跳动。

## content-visibility: auto 适合解决什么问题？

适合长列表、信息流等屏外独立内容：浏览器可跳过暂不相关子树的渲染工作。为减少占位尺寸变化，配合合理的 contain-intrinsic-size；通过滚动、焦点、查找与屏幕阅读器实测验证体验。

> 坑：认为它等于 display:none 或可无条件套在任意容器。

## will-change 是否应随处添加？

仅在短时、可预测动画前后按需提示，并在结束后移除；先由 trace 证明瓶颈。它可增加内存/合成负担。

## content-visibility 跳过离屏工作

auto 可延迟离屏元素的布局与绘制，同时保留可访问性树语义。

> 坑：它等同于 display: none。

## 何时选 content-visibility，何时选虚拟列表？

机制/边界；静态/中等长度内容可先用 CSS 跳过渲染；超长动态列表需回收 DOM、测量行高和保持滚动定位。 取舍：虚拟化增加焦点、搜索、可访问性和高度估算复杂度。

> 坑：任何长列表都先引入虚拟化库。

# 多端一致性与验证

## Web 与 React Native 如何共享表单业务并验证差异？

把字段规则、错误码、DTO 和测试向量放进平台无关的 TypeScript 包；平台层分别实现 UI、焦点、键盘、权限、存储和网络适配。

> 坑：共享组件代码越多越好，或用 jsdom 推断原生行为。

## Web、RN、uni-app 如何共享流式能力契约

定义 transport 接口和能力矩阵：web fetch stream/EventSource，RN/uni-app 按版本验证；不支持真流时降级轮询、分段接口或原生模块。

> 坑：所有 JS 运行时都有同样的 Fetch/Web Streams。

## 怎样安全升级 React Native？

> 坑：只在模拟器通过，或只升级 JS 包不核对原生工具链。

# 指标与度量

## CLS 来自无预留尺寸

图片、字体和异步插入内容若未预留空间会导致布局偏移。

> 坑：图片加载快就不会有 CLS。

## INP 关注整次访问中的响应一致性

INP 观察点击、触摸和键盘交互到下一次绘制的延迟，取一次访问中最慢交互附近的代表值，而非平均值。一次交互可拆为 input delay、event processing、presentation delay；目标通常看移动/桌面分别统计的第 75 百分位。

> 坑：首屏快或平均点击快，就代表 INP 一定好。

## INP 慢时先看哪三段

先在 RUM 按路由、端、版本、交互目标记录 INP 与 attribution；再用 DevTools 复现同一流程，分别查输入延迟的长任务、回调处理耗时、呈现阶段的 style/layout/paint。优化后比较 p75 与尾部，不只看本机单次。

> 坑：只压缩事件函数，忽略交互前长任务或回调后的大布局。

## 怎样从 INP 开始排查慢点击？

RUM 采集 p75 并按设备/路由/交互分组；在 trace 复现，削短 handler、拆长任务、减少同步渲染和无用 DOM 更新，复测现场指标。

## 前端如何把性能预算放进 CI，而不是靠手工截图？

对关键路由和设备档位定义预算（如 LCP/INP/CLS、JS 体积、图片体积），在可重复的 lab 测试中采集趋势；PR 对超阈值给出失败或豁免原因。上线后用 RUM 按路由、设备、网络分位数验证，并用 feature flag/回滚策略处理回归。

> 坑：只看平均值；只压缩 bundle 而不看关键路径。

## 图片与字体如何减少 CLS，又不牺牲首屏？

对图片/广告/嵌入内容预留可预测尺寸或 aspect-ratio；响应式图片提供合适的 srcset/sizes；只预加载经证实的关键资源。字体定义合理 fallback 与 font-display 策略，测量替换导致的偏移，关键文案必要时做度量匹配。

> 坑：一律 preload 全部字体；把懒加载用于首屏 LCP 图。
