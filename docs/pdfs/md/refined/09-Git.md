# 提交与历史

## CI 中如何处理 flaky test 而不掩盖缺陷

单独标为 flaky，保留首败与重试的 trace、seed、run、浏览器和提交；先复现并定位共享状态、未等待异步、时间/网络依赖。必要时限时 quarantine 且有 owner/期限，但关键安全和数据完整性测试不得靠重试放行。

> 坑：提高 timeout、无限重试、删掉偶发测试。

## React Compiler 如何灰度并证明收益

先修 Rules of React；按目录/annotation 小范围启用；单独提交配置与代码修正；建立行为回归、Profiler/真实用户指标和 bundle/build 指标；feature gate/A-B 灰度，异常可快速关停。

> 坑：构建成功或 render 次数下降就等于用户体验提升。

## Release 分支如何回退有依赖的多提交改动

先画提交/功能依赖并确认已合并拓扑；能关 flag 先隔离；代码按逆依赖顺序 revert，merge commit 明确 mainline；解决冲突后重跑目标页面、历史记录、权限和视觉测试；配置/数据变更有独立回退方案和审计记录。

> 坑：直接 reset/force-push；只看文件数量决定可独立回退。

## Revert 是追加反向提交而非抹除历史

git revert 根据既有提交生成反向变化并创建新提交，适合已共享历史。先识别目标及后续依赖，必要时按逆依赖顺序回退；冲突解决后重新跑门禁。

> 坑：revert 等价 reset，或回退一个功能提交一定能独立恢复系统。

## cherry-pick 最小提交的前提？

机制/边界；提交必须尽量自洽，先检查依赖顺序与工作树，冲突后验证 index/内容并运行最窄检查。 取舍：跨分支回放会产生新提交 ID；公开回溯可用 -x。

> 坑：按日期盲选一串提交。

## 乐观状态是临时投影，不是新的事实源

useOptimistic 在 Action pending 期间将临时更新叠加到当前权威 value 上。成功后权威 value 收敛，失败后回到当前 value；reducer 可在基线变化时重新计算投影。

> 坑：乐观更新成功显示即代表服务端提交成功，或失败时只要把本地布尔值取反即可。

## 交互性能优化如何提交、发布与回滚

先保留可复现基线；将测量埋点、行为修复、纯样式优化按可审查边界提交，CI 跑功能/无障碍/性能预算；按版本灰度，比较相同人群的 INP p75、长任务、布局/绘制和错误率，异常用开关或提交回滚。不得用平均值或单次 Lighthouse 代替 RUM。

> 坑：代码行数减少或构建通过就是性能收益。

# 分支与合并

## 上传四态是最小状态机

idle、uploading、success、error 互斥，进度和已上传资源属于对应分支。

> 坑：多个 boolean 任意组合。

## 乐观更新怎样避免双写、乱序和冲突？

每次 mutation 有稳定 client mutation id 与 idempotency key；本地以可回滚补丁记录前置版本，队列按实体/依赖排序。服务器以幂等键去重并返回权威版本；版本冲突时停止该实体队列、展示差异或走业务合并，不能盲目覆盖。

> 坑：onError 直接回滚整个 cache，误删后续成功操作。

## 乐观状态是临时投影

useOptimistic 在 Action 进行时把待确认动作投影到权威状态之上。成功后权威 value 前进，失败后临时层消失并回到当前权威值。

> 坑：乐观 UI 等于本地先永久写入。

## 交互修复如何随 release merge 做回归与回滚

# 回滚与恢复

## Git 如何让异步重构便于审查和回滚？

拆为可验证提交：请求客户端/状态机测试、单页面接入、开关与观测。PR 展示乱序、abort、超时、服务端已写入等证据；CI 跑单元/集成/关键 E2E。回归用 flag 或可逆提交止血，保留 trace/请求 ID。

## 删除旧实现怎样保证可回滚？

提交保持单一职责，记录数据兼容边界与替代路径，发布用开关/分阶段清理，必要时可独立 revert。

> 坑：把新旧实现一次重写到一个大提交。

## 如何把一次响应式重构拆成可回滚的 Git 协作链？

先补行为测试与性能基线；按“抽 composable → 接入一页 → 扩展调用方”分小提交，提交信息可独立回滚。PR 说明状态机、取消行为、迁移开关与观测指标；用 feature flag 灰度，出现错误率/TTI 回归则关闭开关或 revert 对应提交。

> 坑：巨型格式化混入逻辑重构；把 rebase 当线上回滚方案。

## 如何用 Git 交付一次可回滚的设计系统样式迁移？

先写视觉/交互基线与影响面，按 token、组件、页面分小提交；每步包含视觉回归、键盘/读屏与性能验证。用 feature flag 或双样式兼容窗口逐步放量；回滚需要包含 CSS/组件版本、缓存失效与监控阈值，不能只说 git revert。

> 坑：单一巨型 PR；把 Git 回滚等同于用户已加载资源的即时回退。

## 如何通过 Git 安全交付一次 RSC/离线改造？

拆为边界清单、DTO/鉴权、持久化迁移、读缓存、写队列、监控与开关；每步保留兼容读取和数据迁移版本。PR 必带 bundle diff、缓存键变更、威胁模型、E2E 场景与回滚方案。

> 坑：把 feature flag 只包 UI，不包重放器和新 schema 写入。

# 审查与 diff

## Git bisect 如何在测试不稳定时产出可信回归证据

固定环境、数据和入口，先让判定脚本在已知 good/bad 多次稳定；bisect 每点运行同一 oracle，对不可构建或不确定提交用 skip，不把一次失败定 bad；找到首个嫌疑后手工复现、阅读 diff，并以 revert/补丁 A/B 验证因果。

> 坑：构建失败一律 bad；bisect 找到的提交自动等于根因。

## Git 证明要分层

diff 证明文本变化，构建证明静态链，测试证明断言，浏览器证明运行路径。

> 坑：CI 绿等于用户场景必定正常。

## 如何从大 diff 中排除格式化噪声？

机制/边界；先看 stat/文件范围，再用 ignore-space 作为辅助，最终回到真实 patch 与行为验证；不要让噪声掩盖语义。 取舍：忽略空白视图不能用于判断字符串/缩进敏感文件。

> 坑：只看 --stat 就审完。

## 如何从格式化噪声中审查真实 Git 变更

先按文件与统计确认变更范围，再用忽略空白的 diff 看语义变化；必要时使用 word diff、移动检测与 AST/类型检查。最佳治理是把纯格式化提交与功能提交分开，并在合并前跑格式检查，使后续提交保持小而可审查。

# 发布与版本

## ETag 如何同时服务缓存验证与并发写保护？

读响应给出表示版本的 ETag，缓存过期时用 If-None-Match 验证；写入可带 If-Match，服务端仅在版本匹配时执行，否则返回前置条件失败，让客户端刷新/合并/提示冲突。版本应由服务端权威生成。

## 版本校验防静默覆盖

更新携带 version/ETag，服务端不匹配返回冲突，客户端提示刷新/合并。

> 坑：拿到 409 就重复提交。

## 自动保存是版本化写协议

自动保存至少需要 dirty revision、在途请求、成功确认和失败重试四类状态。保存启动时捕获 revision；只有返回时 revision 未变化才标记 saved，否则保持 dirty，避免旧回包伪装成最新成功。

> 坑：请求 200 就能清除所有 dirty，或 debounce 能自动保证顺序与不丢数据。
