# 流与背压

## Node Writable.write 返回 false 后该做什么

chunk 已被接收进缓冲，但缓冲达到阈值；生产者应暂停读取/生成，等待 drain 再继续。优先使用 pipeline() 让错误、关闭和背压统一传播。

> 坑：false 表示写失败并应立即重试同一 chunk；或无视 false 继续写。

## Node events.once() 为什么可能漏事件？

emit 同步调用监听器。若连续 await once('a') 再创建 'b' 监听，而两事件都在同一轮/nextTick 发出，Promise 续体未运行，第二个监听尚不存在，b 就会丢。

## Node 如何应对慢订阅者？

每连接限制队列字节数，低优先级事件合并或丢弃并要求重取快照；观察 socket bufferedAmount/drain，心跳超时清理；广播由队列/总线解耦，避免业务请求同步 fan-out。

> 坑：为每位用户无界缓存所有事件。

# 取消与超时

## AbortSignal 是一次性取消状态

signal 从未取消单向进入已取消，并携带 reason。消费者检查 aborted/throwIfAborted()，或监听一次 abort；组合信号表达“任一上游取消”。

> 坑：AbortController 可 reset，或触发 abort 就证明 socket、定时器、流都已释放。

## BFF 如何做超时、降级和部分成功？

对每个依赖设预算、超时和取消传播，隔离慢依赖；可独立展示的数据并行聚合，失败项按 UI 契约返回可识别状态（available stale），而非整页 500。缓存需带版本/TTL 和权限维度，trace ID 贯通。

> 坑：无限重试或静默吞错显示空数据。

## Node fetch 收到 headers 后取消时还要考虑什么

fetch fulfillment 只表示 headers 可用，body 仍是异步流。读取阶段继续传递/遵守 signal，取消后确认 reader/body 被取消或消费、错误被观察、业务状态不再提交，并通过活跃句柄、连接池和内存指标验证释放。

> 坑：Response 到达等于下载完成；abort 后忽略 body；从关闭 issue 推断所有版本都无风险。

## Node 服务如何把超时、客户端断连与主动取消统一到 AbortSignal ？

每个请求建立/继承 signal；把客户端断连、业务 deadline 和上游取消组合后传入 fetch、DB/SDK（仅限其明确支持时）。监听取消后停止下游工作并释放资源；将已知取消分类为 cancelled/499 类观测，不与 5xx 混算。

> 坑：捕获所有错误后返回空数组；超时后继续重试非幂等写；把 abort 当成功。

## Promise.race 超时为什么可能留下后台工作

race 只采用最先结算的结果，不会取消输掉的 Promise。应让操作接受 signal，超时时 abort，并在 finally 清定时器；非可取消 SDK 需用其取消接口、隔离 worker 或限制并发，不能宣称已停止。

> 坑：忽略迟到 rejection；超时后自动重试非幂等请求；把 UI 停止 loading 当资源释放证据。

# 并发与进程

## Node 服务如何优雅退出且避免 process.exit 截断工作

信号处理器只触发一次关闭状态；停止监听/就绪探针，拒绝新工作；等待在途请求、队列、日志和连接关闭；设置有上限的强制超时；通过 process.exitCode 让事件循环自然收尾，只有不可恢复且超时后才强制退出。
