# Flex 与 Grid 布局

## Flex 与 Grid 的选择标准是什么？

一维的内容分布、对齐或工具栏优先 Flex；同时控制行与列、卡片矩阵或明确网格轨道优先 Grid。先让内容决定高度，必要时用 minmax()、auto-fit/auto-fill 建立可伸缩轨道。

> 坑：用绝对定位拼常规布局；把 Grid 当成性能优化本身。

## content-visibility 的性能与可访问性边界

## content-visibility: auto 能优化什么？

机制/边界；浏览器可跳过离屏内容的布局与绘制，降低初始渲染工作；元素仍参与文档并保留语义。 取舍：滚动跳动需用 contain-intrinsic-size 估算尺寸。

# 响应式与容器

## CSS 的 100vh 为什么在移动端常出问题？

移动浏览器地址栏/键盘会改变可见区域，100vh 的语义与实际可视区域可能不一致。全屏壳可优先用 min-height: 100dvh，并测试键盘弹出、横竖屏和安全区；需要稳定最小/最大语义时评估 svh/lvh。

> 坑：用 JS 每次 resize 写死高度，造成抖动和焦点跳动。

# 动画与降级

## CSS 动画怎样兼顾流畅、可访问与可取消？

定义明确的进入/退出状态，优先动画 transform/opacity；响应 prefers-reduced-motion 提供减弱或瞬时版本；交互中支持取消并在组件卸载时清理监听/动画。将动画视为装饰，不能阻塞完成操作或掩盖加载状态。

> 坑：transition: all、无限动画、只测高端设备。

## prefers-reduced-motion 应如何落地？

机制/边界；用媒体查询降低位移、视差和自动播放运动，保留必要状态反馈；组件库与 JS 动画也要读取同一偏好。 取舍：不是所有用户都要求零动画。

> 坑：仅把 duration 改为 0.001ms。

## transform/opacity 是否一定更快

transform/opacity 通常更有机会避开布局并在合成阶段处理，但是否独立合成、是否重栅格和最终帧率由浏览器、层、内容、滤镜、内存与设备决定；用 Layers/Performance/paint flashing 验证。

> 坑：GPU 是可由 CSS 强制的性能保证。

left/top 可能触发布局并影响依赖几何；transform 通常不改变文档流，可能减少 layout/paint，但是否合成、是否提升 INP/帧率要看元素、效果和浏览器 trace。拖动时 transform，结束时持久化逻辑坐标是常见方案。

# 隔离与渲染

## CSS 自定义属性遵循层叠

同名变量由作用域、层叠层、specificity 与源码顺序决定。

> 坑：最后一个文件永远正确。

## container-type: inline-size 的代价与放置位置？

它让元素成为可按 inline 轴查询的容器，通常放在组件外壳，由内部元素在 @container 中调整。它改变子树与外部布局的尺寸依赖；只在需要的轴建立容器，并让容器的尺寸能由外部约束合理决定。

## contain 的布局/绘制隔离有什么代价？

机制/边界；contain 可缩小样式、布局或绘制影响范围，但可能改变包含块、溢出和尺寸计算。 取舍：按测量选择最小 containment，不要盲目 strict。

> 坑：contain 一定提升性能。

## 评审卡片何时用 Container Query 而不是 Media Query

视口级壳仍用 media query；卡片内部按可用容器宽度切换标题/操作/元信息布局时用 container-type:inline-size 和命名 container。默认样式先可用，再在 @container 增强；断点来自内容崩坏点而非设备型号。

> 坑：所有节点都设 container；只改列数不测溢出、焦点和读屏顺序。
