# 语义与结构

## AbortController 能解决哪些问题，不能解决哪些？

signal 可被 fetch、流和自定义 async API 监听，停止未完成的协作工作；适合卸载、换词、超时和用户取消。它不保证请求未发出、服务端未执行或数据库写入撤销；写路径仍要幂等、可查询。

## Anchor Positioning 是布局增强不是语义关系

CSS Anchor Positioning 让绝对定位元素相对命名 anchor 计算位置，并可定义 fallback。

> 坑：用了 anchor positioning 就不再需要 Popover/Dialog 语义或 JS 状态。

## Chip 是结构化内联节点

显示标签与业务 ID 分离，删除/复制/粘贴要保持原子语义。

> 坑：用 span 文本再正则解析。

## Dialog 与 Popover 如何按模态性选择

轻量筛选/提示通常用非模态 Popover；必须回应的删除确认用 dialog.showModal()；逾期详情按是否允许继续操作决定。语义先于视觉，需验证触发器关系、Escape/取消、焦点返回和不支持能力的降级。

> 坑：Popover 有 backdrop 就是 modal，或 dialog.show() 等价于 showMod…

## Diff 噪声与语义变更

格式化、换行或移动造成的文本差异可能掩盖逻辑变化。原始 diff、忽略空白、word diff、移动检测分别提供不同视角。

> 坑：构建通过就等于 diff 没有行为变化。

## async、defer、module 的执行语义？

机制与工程边界；async 下载完立即执行且不保序；defer 在解析后按序执行；module 默认延迟且模块依赖按图处理。 取舍：动态插入脚本和 top-level await 需另判。

> 坑：module 与 async 完全相同。

## innerHTML 的主要风险与替代？

机制与工程边界；不可信字符串进入 HTML 解析上下文可能触发 XSS；优先 textContent/模板转义，确需 HTML 时使用严格 sanitizer。 取舍：富文本协议要限制 URL、标签、属性。

> 坑：正则删除 script 就安全。

## pending UI 如何兼顾 HTML 语义与动效

真实不可重复提交时用原生 disabled；区域加载可用 aria-busy，关键结果用合适 live region；保留稳定尺寸避免布局跳动，并尊重 prefers-reduced-motion。

> 坑：只降低 opacity，或给所有更新都用 assertive live region。

## pipeline

pipeline 统一传播多段流的错误并负责销毁。

> 坑：pipe 与 pipeline 的错误语义完全相同。

## script async、defer、module 加载语义

默认外部经典脚本遇到时抓取并执行，阻塞 HTML 解析。async 并行下载、下载完尽快执行，多个脚本不保证文档顺序，适合相互独立脚本。defer 并行下载，解析完成后按文档顺序执行，并延后 DOMContentLoaded。

## 如何为 SPA 路由切换设计焦点与标题？

路由完成后更新 document.title，把焦点移到页面主标题或主内容容器（通常 tabindex="-1"），并提供跳到主内容的 skip link。这样键盘和读屏用户不会从旧导航位置“迷路”。

## 何时用语义 HTML，而不是用 div 加 ARIA？

原生元素已表达意图时优先使用它：导航用 nav、主内容用 main、可触发动作用 button、跳转用 a[href]、表单控件用对应 input。它们自带键盘行为、焦点、可访问名称与浏览器默认语义；ARIA 用来补足不能用原生元素的复合组件，而非重造按钮。

> 坑：role="button" 不会自动获得 Space/Enter 行为；点击 div 不是可访问按钮。

# 表单与控件

## DrawIO 画布

嵌入画布要定义消息来源、保存协议、退出确认和版本兼容。

> 坑：iframe 内应用天然可信。

## HTML 约束验证是交互层而非安全边界

required、type、min/max、pattern 等构成原生约束，ValidityState 描述失败原因。

> 坑：前端按钮 disabled 或浏览器校验通过就代表数据可信。

## React/Vue 中受控、非受控表单如何选择？

需要即时派生 UI、跨字段联动或统一状态管理时使用受控值；以原生表单/FormData 为主、字段很多或只在提交读取时，可采用非受控引用。无论框架，验证规则、默认值、reset 和服务端错误映射要有单一事实来源。

> 坑：受控一定更高级；非受控就无法校验。

## Web/RN 共用表单逻辑时必须分层什么？

共享 schema、错误码、状态机、埋点和纯校验；DOM 语义/原生验证/焦点、文件选择与 RN 输入/读屏/列表留在平台层。共享层契约测试，宿主做浏览器与真机验证。

## form.submit() 、点击 submit 按钮和 requestSubmit() 有何区别？

用户点击 submit 控件会走交互式约束验证，成功后触发可取消的 submit 事件；requestSubmit() 模拟指定提交控件的正常提交流程。

> 坑：preventDefault() 会让表单自动变有效；所有提交 API 行为相同。

## fieldset、legend、label 与 autocomplete 如何组成可访问表单契约

每个控件有稳定 label/name；相关单选/复选用 fieldset+legend 分组；autocomplete 使用规范 token 表达字段目的；错误文本通过稳定 id 与 aria-describedby/aria-errormessage 关联…

> 坑：只给容器 aria-label；用 placeholder 当永久标签…

## 为什么“能点击的 div”不是按钮的等价替代？

优先用 <button>：浏览器已提供可聚焦、Enter/Space 激活、禁用语义、可访问角色和名称。把 div 加 onClick 只覆盖鼠标；若确有自定义控件，必须补角色、可访问名称、Tab 焦点、键盘激活、禁用状态与可见焦点，但维护成本更高。

> 坑：tabindex="0" 就“无障碍了”。

## 上传生命周期

文件上传包含选择、校验、传输、确认、失败恢复和最终关联。

> 坑：进度到 100% 就可关闭页面。

## 为什么优先使用原生 form 、 label 、 button ，而不是 div 拼交互？

form 提供提交语义，label 将可见文案与控件关联，原生 button 有焦点、键盘和禁用行为。它们让浏览器、辅助技术和无 JavaScript 场景共享同一基础流程；复杂视觉可在其上封装组件。

> 坑：role="button" 自动拥有 Space/Enter 行为…

## 列表更新时为何不能把 index 当 key ？

key 表示逻辑身份；插入、排序或过滤时 index 会让旧 DOM/组件状态与新数据错配。使用稳定的业务 ID；没有稳定 ID 时，先设计数据 identity，而非用 index 掩盖。

> 坑：认为 key 只是为了消除警告或提升性能。

## 前端如何设计“提交后才显示错误”的可访问校验体验？

首次提交失败后聚焦首个无效控件或错误摘要，再用已关联的错误文本（例如 aria-describedby）说明字段问题；之后在 blur 或下一次输入中按规则更新。保留原生语义、可见 label、足够对比度，并让错误摘要链接到对应字段。

> 坑：只靠颜色区分错误；把错误文本放在视觉上很近但 DOM 上无关联的位置。

## 原生 Constraint Validation 如何与业务 Schema 和服务端校验协作

用语义 input 与原生属性承担即时、低成本约束；跨字段规则用 setCustomValidity 或受控错误；提交用 requestSubmit() 走原生流程；服务端按主体、对象和业务 schema 重验并返回字段/表单级错误。

> 坑：checkValidity() 会显示消息；HTML 校验通过可跳过后端…

## 原生约束验证（Constraint Validation）能做什么，不能做什么？

required、合适的 type、min/max/step、minlength/maxlength、pattern 等表达基础约束；控件可通过 validity、checkValidity()…

> 坑：pattern 是任意输入类型的万能正则；客户端通过即代表数据可信。

## atom、isolating、selectable 与 draggable 怎么选

atom 让节点按整体处理，isolating 阻止部分边界合并，selectable 控制 NodeSelection，draggable 控制拖拽；需按复制、删除、键盘导航和无障碍需求组合，而非模板化全开。

> 坑：这些 flag 只是视觉配置。

## dialog 与 popover 的核心差异是模态性

dialog.showModal() 进入 top layer 并使其余文档 inert；Popover 通常是非模态浮层，支持声明式触发和 light dismiss。按用户是否必须先处理当前内容选择，而不是按视觉是否有遮罩选择。

> 坑：给 Popover 画深色 backdrop 就成为 modal，或所有浮层都应使用 dialog。

## focus-visible 与 focus 有何差异？

机制/边界；focus 表示焦点状态；:focus-visible 由 UA 启发式决定何时显示明显焦点环，适合保留键盘可见性。 取舍：不要通过 outline: none 移除所有焦点反馈。

> 坑：鼠标点击不显示就等于元素不可聚焦。

## reduced motion 是替换非必要运动

prefers-reduced-motion: reduce 表示用户请求减少、移除或替换非必要运动。保留状态变化、焦点和结果反馈，缩短/取消大幅位移、缩放、视差和连续循环。

> 坑：无动画就天然无障碍，或动效只是审美问题。

## 一个真正的模态对话框需要满足哪些焦点条件？

打开时焦点进入对话框内合适的元素；Tab/Shift+Tab 不离开其可聚焦范围；Escape 有明确关闭策略；关闭后返回触发者，除非触发者消失或后续工作流有更合理去处；背景对所有用户均不可交互。对话框要有可访问名称和可见关闭操作。

> 坑：只加遮罩/aria-modal，但背景仍可点击或 Tab 仍能逃逸。

## 何时该用 ARIA，何时不该用？

ARIA 用来补足没有等价原生语义的复杂 widget 或动态状态；能用原生 HTML 就用原生 HTML。添加 role/state/property 后，开发者必须实现与其匹配的键盘行为、状态同步和焦点管理。

> 坑：给所有元素都加 role，或把 aria-label 当成修复语义结构的万能贴纸。

## 动效怎样兼顾状态与可访问性

默认使用短、可中断的状态过渡；reduce 时移除大幅移动/缩放并保留即时显隐。打开后把焦点移到可理解的标题/首个控件，关闭后还给触发器；状态不能只靠动画或颜色表达，异步结果用合适语义通知。

> 坑：把 animation-duration: 0s 当作完整无障碍方案。
