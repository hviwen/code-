# 依赖、构建与产物

## CI gate 应如何分层？

机制/边界；快速 lint/typecheck 先反馈，单测/构建随后，关键集成与浏览器 smoke 再兜底；每层明确证明边界。 取舍：更全的 gate 更慢，应按风险和并行成本安排。

> 坑：只保留一个全量 job。

## Corepack

Corepack 根据 packageManager/锁定版本提供包管理器，CI 需显式启用并固定版本。

> 坑：全局 pnpm 版本无关紧要。

## base 路径为什么会让多页入口失效？

构建产物的资源/路由基址与部署子路径不一致会导致 404；多页入口还受平台托管规则约束。

> 坑：改相对路径即可覆盖所有场景。

## lockfile 是解析快照

它记录具体版本、完整性与依赖图；大 diff 不等于每行都有业务意义。

> 坑：手工删冲突块就完成修复。

## lockfile 是解析结果快照

记录依赖解析结果、peer 组合与完整性信息。安装器结合 manifest、配置、工具版本和 lockfile 构造依赖图。

> 坑：大 diff 一定代表所有依赖升级；正确做法是比较解析结果。

## peerDependency 决定宿主兼容区间

插件包依赖宿主提供的同一框架实例/版本；不一致可能产生缺失导出或重复实例。

> 坑：只升级报错包，不查消费者。

## pnpm lockfile 升级如何保证可复现构建

先把“包管理器升级”和“依赖升级”拆开。

## 云构建

云构建要固定运行时、包管理器和 lockfile，记录产物与日志。

> 坑：CI 失败时反复重跑即可。

## Tiptap 扩展版本错配为何会出现 missing export？

## Tiptap 正文应存 JSON 还是 HTML

> 坑：存两份却没有 source-of-truth；扩展改名后不迁移旧 node type…

# 回滚与恢复

## Git 如何让类型重构可审查、可回滚？

把“新增契约/adapter、迁移调用方、删除旧路径”拆为可构建提交；每步带类型检查和关键行为测试。PR 写清兼容窗口与回滚方式；用 feature flag 或双读比对降低风险。

> 坑：只凭 tsc 通过就认为迁移成功；将 git reset --hard 作为冲突解决方案。

## 乐观更新怎样做到可回滚？

生成 mutationId，记录前态和目标版本，立即展示临时值；响应成功以服务端快照确认；失败仅在该 mutation 仍是当前写入时回滚。并发写入冲突时失效重取或基于版本重放，不能无条件恢复旧对象。

> 坑：失败后把整个列表替换为旧快照，覆盖后续成功操作。

## 乐观标题更新必须可回滚
