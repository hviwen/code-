# 测试分层与策略

## API 版本

版本升级应明确路径、schema、兼容窗口和回滚策略。

> 坑：改成 /v2 即完成迁移。

## 如何为高风险前端流程设计测试分层？

先列关键资产、失败模式和可观察结果，例如支付金额、重复扣款、认证过期、回调乱序。纯函数/校验规则用快速单测；组件与请求状态用集成测试；支付、登录等少量关键旅程用真实浏览器 E2E；服务边界用合约测试。每层都写清证明什么、不能证明什么，以及失败证据。

> 坑：“E2E 最真实，所以全靠 E2E”。

## 单测、集成、E2E 分别要证明什么？

单测证明一个受控单元在明确输入下的规则；集成测试证明多个真实协作单元（渲染、状态、请求适配器）能得到用户可见结果；E2E 证明部署后关键旅程在浏览器和真实协议条件下可完成。三者不是互相替代。

> 坑：把“覆盖率高”当成行为已经验证。

## 如何处理 E2E 的并行、数据隔离和失败证据？

为 worker 分配独立租户/账号/测试数据前缀；每例创建与清理数据，避免共享可变状态；密钥由 CI 安全注入；失败时保存 trace、截图、视频、网络与服务端关联 ID。重跑只用于判别 flaky，不能掩盖首失败。

## 怎样测试 RSC 与离线状态机？

单测覆盖 DTO 映射、可序列化检查、队列状态转移和冲突归类；集成测覆盖 server/client 边界、鉴权与 idempotency；E2E 在真实浏览器或设备模拟首次启动、两次离线重启、网络抖动、会话过期、重复提交和升级迁移。

> 坑：只 mock navigator.onLine，不控制实际请求失败与恢复次序。

## 测试层级按失败成本和证据选择

单元测纯逻辑，组件测用户可见交互，契约测边界格式，集成测真实协作，E2E 测关键业务路径。把多数边界条件放在快速确定性测试，少量关键路径留给浏览器/真实依赖。

> 坑：所有行为都上 E2E，或单测通过即等于页面可用。

## 为什么测试用户可见行为而非实现细节？

用户关心可访问名称、输入、反馈和可提交结果；以它们定位可在重构组件层级、state 管理或 hook 时保持测试价值。用角色/标签查找元素，断言状态和副作用；只在公共契约确实是实现级 API 时测试该 API。

> 坑：断言私有 state、class 名或 setState 次数。

## 评审功能应在哪些层测试

纯 parser/model/轮询状态转移做快速单元与属性测试；请求方法、路径、body、错误格式做契约测试；组件以可访问角色和用户操作验证 loading/success/error/permission；E2E 只覆盖创建→轮询→通过/驳回…

> 坑：按代码文件一比一造测试，或只追覆盖率。

## 如何验证实时功能已可上线？

单测事件 reducer；集成测试重复、乱序、401、版本冲突；E2E 模拟双用户/弱网/后台切换；灰度开关与协议兼容矩阵；依据同步 p95、补快照率、错误率决定扩量或回滚。

> 坑：只测两台浏览器连接成功。

# 隐私与脱敏

## Server Component 向 Client Component 传值有哪些约束？

跨边界 props 必须可序列化；传最小 DTO，不传任意函数、类实例、连接、秘密或未经授权的原始记录。事件行为放 client，敏感动作通过受控 server 接口再次鉴权。

> 坑：把 ORM 实例或包含 token 的用户对象直接传给 client。

## 双身份测试如何证明对象级授权

A 创建对象 XA，B 创建 XB；验证 A→XA、B→XB 成功，A→XB、B→XA 在详情和动作路径被服务端拒绝，再覆盖跨租户、批量和不存在对象。断言无敏感 body、无副作用、审计事件正确；token 从受控测试环境注入且报告脱敏。

> 坑：仅换数字 ID、仅测按钮隐藏或复用管理员 token。

## 授权测试需要至少两个真实身份

用主体 A 创建/拥有对象，再由 B 访问同一对象，验证服务端拒绝；再验证 A 的合法路径。覆盖列表、详情、动作、批量、导出和错误差异，并确保 token、租户和对象真实对应。

> 坑：返回 404/403 任一状态就足以证明无 BOLA，或 UUID 无法猜测即安全。

## 错误日志

前端日志要结构化记录时间、版本、路由和错误链，并脱敏。

> 坑：直接记录请求正文最利于排障。
