# HTTP 与缓存

## AbortSignal 是协作式取消

signal 传播取消意图，消费方必须监听并尽快停止可取消工作。浏览器 fetch、Node 下游 fetch/任务共享信号或派生信号；取消按 AbortError 单独处理。

> 坑：组件卸载后请求和服务端计算自然停止。

## Context、外部 store 与请求缓存如何边界化？

Context 放主题、当前身份等低频稳定依赖；高频订阅状态用具备 selector 的外部 store，避免 Provider value 改动波及大树；请求缓存负责远端数据的键、失效、重试与竞态。边界以更新频率、所有权、可持久性和服务端权威性决定。

> 坑：将所有后端数据塞进全局 store，或认为 Context 天然性能差。

## DOM 重建为何让光标跳到句首？

响应式重渲染替换文本节点，原 Range 指向旧节点；恢复逻辑又以容器开头兜底。

> 坑：setTimeout 聚焦末尾即可。

## External store 的快照必须可比较且稳定

useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?) 把 React render 接到外部事实源。

> 坑：每次 getSnapshot() 返回 {...state} 更安全；实际会造成无意义更新甚至循环。

## Fetch 只在网络层失败时 reject

HTTP 404/500 通常仍得到 fulfilled Response；response.ok 只在 200–299 为 true。

> 坑：进入 .then 就表示业务请求成功。

## Fetch 错误如何统一成 Problem Details

先区分 AbortError/网络失败与已收到 Response；检查 ok、status、Content-Type。

> 坑：只 catch fetch，或所有错误都 response.json()。

## HTTP 缓存不等于 bfcache

HTTP 缓存复用响应；bfcache 恢复页面快照。HTTP 通过 freshness 与条件请求校验；bfcache 可恢复 JS/DOM 状态。

> 坑：no-cache 等于不保存。

## HTTP 缓存的 freshness、validation 与 invalidation 有何区别？

freshness 由 max-age 等决定缓存能否直接复用；过期后可带 If-None-Match/If-Modified-Since 做 validation，未变得到 304 并复用实体；invalidation 是应用/CDN 等主动使条目不再可用。

## HTTP 缓存：no-cache、no-store 与 immutable

HTML 通常使用 no-cache 允许存储但复用前校验，确保能发现新资源入口；带内容 hash 的静态资源使用长 max-age + immutable；私有响应根据敏感性使用 private, no-cache，确实不应存储时才用 no-store。

## HTTPS 页面会限制混合内容

安全上下文加载 HTTP 子资源会被升级或阻止，API/iframe 地址需按环境统一。

> 坑：CORS 配好就不会混合内容。

## 为什么 HTTPS 页面请求 HTTP API 会失败？

这是混合内容限制，发生在安全上下文资源加载层；即使 CORS 允许也可能先被浏览器阻止。

> 坑：只改 Access-Control-Allow-Origin。

## Node Stream 与 Web Streams 如何互操作

使用 Readable.fromWeb/toWeb、Writable/Duplex 对应适配器；在边界统一 chunk 类型、错误、取消和 objectMode，避免整流读取后再包装。

> 坑：两个 API 名称相似即可直接 pipe。

## Node 聚合接口应记录哪些观测信号，才能定位缓存/一致性问题？

为请求传播 trace ID，并记录 route、缓存层/命中状态、上游耗时、重试/取消、响应版本（脱敏）、错误分类；用 span 表达调用链，以 metrics 观察命中率、P50/P95/P99、错误率和陈旧读比例。

## RSC/Next 数据缓存应如何与写操作连接？

先界定数据身份、读写路径、用户/租户作用域与新鲜度；将可缓存读取置于细粒度函数或边界，写成功后按资源身份失效/更新并验证导航、刷新和多实例行为。缓存不是授权边界。

> 坑：用一个宽泛 tag 清空全站，或以为 mutation 后 UI 必然同步。

## 为什么 SSR 中的副作用要格外谨慎？

SSR 每个请求必须拥有隔离状态；服务端渲染期间不应启动长期轮询、浏览器 API 或无界 watcher。把数据获取放在框架约定的 SSR 数据层，并在请求结束释放资源；客户端 hydration 后再启动浏览器副作用。

> 坑：在模块顶层缓存每个用户的响应式 store。

## Service Worker 不能替代应用级一致性策略，为什么？

Service Worker 擅长拦截导航/静态资源与定义请求缓存策略，但不理解用户、租户、授权、写入顺序或业务冲突。应用仍要为 API 数据定义 cache key、失效、鉴权切换、加密/清除和 mutation outbox。

> 坑：“装了 SW 就天然离线可编辑”。

## Service Worker 缓存怎样避免旧壳锁死？

机制与工程边界；版本化缓存、安装/激活迁移、网络失败回退与可观测更新提示；HTML 壳通常采用网络优先或严格再验证。 取舍：skipWaiting 会加速更新但可能造成新旧资源混用。

> 坑：cache-first 用于所有请求。

## Vue SSR 中副作用、单例和请求状态如何隔离？

每个 HTTP 请求创建 app、router、store 与 request context；不要把用户数据写进模块级 reactive 单例。

## Cache-Control: no-cache 与 no-store 如何选？

no-cache 允许保存但每次复用前必须向源站验证，适合希望缓存协作但不能直接使用陈旧表示的 HTML/API；no-store 要求不存储，适合含高度敏感数据的响应。

## Vary 为何会造成“有的用户拿到错内容”的缓存事故？

共享缓存需将会改变表示的请求头纳入变体键，例如语言内容依赖 Accept-Language 则响应声明 Vary: Accept-Language。个性化、鉴权响应通常避免被共享缓存，或采用明确的私有/受控策略。

## bfcache 恢复为何会出现陈旧 UI，怎么处理？

bfcache 命中后，DOM 与 JS 堆可从冻结态恢复，组件“重新挂载”假设失效，时间敏感数据、会话和连接状态可能过期。

## no-cache、no-store、private 如何选择？

机制与工程边界；需验证后复用用 no-cache；完全不存储用 no-store；个性化但允许浏览器缓存用 private，并配合验证器。 取舍：旧缓存不会因新响应 no-store 自动删除。

# 通信与事件

## EventSource 自动重连是否足够？

自动重连只恢复传输；业务仍需事件 ID、游标、去重、鉴权刷新和断点过期处理。

> 坑：重连成功等于消息完整。

## SSE 分帧

> 坑：用换行 split 即可覆盖所有流式边界。

> 坑：刷新后永远进入 streaming。

EventSource 从服务端推送文本事件，浏览器自动重连；写请求仍走 HTTP 或其他通道。

> 坑：把 SSE 当双向 WebSocket。

## SSE 生命周期

暂停应关闭连接，发送时按会话状态重连并恢复水位。

> 坑：EventSource 会自动恢复所有业务状态。

## SSE 的 data、id、retry 与重连如何工作

每个事件以空行结束，可含 event/data/id/retry；多行 data 按规范合并。浏览器重连可携 Last-Event-ID，服务端用事件日志从下一序号重放，客户端仍要去重。

> 坑：TCP 重连会自动恢复所有业务事件。

## SSE 连接何时应该关闭？

业务完成、会话删除、无消费者且无输出、鉴权失效或页面销毁时关闭；生成中切视图可按策略保活。

> 坑：路由一变就关闭所有连接。

## SSE 连接属于会话资源

连接应由会话 ID、输出状态和页面生命周期共同管理，并在不需要时关闭。

> 坑：组件卸载后浏览器一定立即释放一切。

## SSE 重连时怎样避免重复消息？

机制与工程边界；服务端提供事件 ID/游标，客户端按 messageId 幂等合并；重连携带 Last-Event-ID 或显式游标。 取舍：代理可能缓冲；心跳只保活，不能证明业务消息完整。

> 坑：收到事件就 push。

## WebSocket、SSE、轮询怎么选？

SSE 是服务端到客户端的单向、HTTP 友好流；WebSocket 适合双向协作；轮询适合低频、可接受延迟且易经由现有 HTTP 基础设施的场景。传输层选择后仍要设计事件 ID、重连、鉴权和降级。

> 坑：“WebSocket 天然可靠、有序且永不丢”。TCP 顺序不等于重连跨会话的业务顺序。

## chunk 边界不等于字符或消息边界

> 坑：每个 chunk 都能直接 JSON.parse。
