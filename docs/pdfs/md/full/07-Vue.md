## React/Vue 如何避免“慢旧响应覆盖快新响应”？

**考察意图**

请求生命周期与 UI 一致性。

**核心答案**

将查询参数和请求版本绑定；参数变更/卸载时 cleanup 旧请求并 `abort`，提交前确认仍为当前版本。React effect 需对称 cleanup；Vue watcher 在异步工作开始前注册 cleanup。成熟数据层可处理缓存/去重，但业务仍要定义旧数据显示与错误归属。

**追问**

如何写一个“旧请求最后返回”的确定性测试？

**边界/误区**

abort 不保证服务端读写未发生；不应把所有异常都吞成取消。

**来源/审校**

learning-vue3、Interview Handbook、React/Vue 官方；**已准入**。

## Vue 为什么批处理更新， nextTick() 究竟等待什么？

**考察意图**

识别响应式变更、组件更新与浏览器渲染的边界。

**核心答案**

同一轮同步状态修改会被 Vue 合并并调度组件更新，避免重复 patch。`await nextTick()` 等当前已排队的 Vue DOM 更新完成，适合读取更新后的 DOM 或衔接依赖它的逻辑。

**追问**

连续两次 `nextTick` 能否证明用户已看到内容？

**边界/误区**

它不等待 fetch，也不保证下一帧已绘制；需要观察布局/动画首帧时，再使用合适的 `requestAnimationFrame` 和实际测量。避免把业务时序建立在多层 tick 链上。

**来源/审校**

learning-vue3、现代 JavaScript 教程、Vue API；**已准入**。

## Vue 批处理、nextTick 与 watcher flush

**问题**

修改响应式状态后为什么立即读取 DOM 可能还是旧值？nextTick、flush: post 和同步 watcher 怎么选？

**核心答案**

Vue 会把同一轮中的组件更新和 watcher 任务批处理，避免重复渲染。一次状态变更后需要读取对应 DOM，用 await nextTick()；某个 watcher 每次都要在组件 DOM 更新后执行，用 flush: post；flush: sync 不批处理，只适合简单、低频数据，数组等高频同步变更会造成重复执行。

**边界与取舍**

- nextTick 等的是 Vue DOM 刷新，不保证网络请求或任意 Promise 都完成。
- 不要在 onUpdated 中无条件改状态，否则可能循环更新。
- Vue 3 的响应式核心是 Proxy；把 Vue 2 的 Object.defineProperty 机制套到 Vue 3 属于过时结论。

**追问**

异步 watchEffect 在第一个 await 之后访问的依赖会被自动追踪吗？为什么？

## computed 、 watch 、 watchEffect 如何分工？

**考察意图**

区分派生状态和副作用，避免把网络请求塞进计算属性。

**核心答案**

`computed` 是可缓存的同步派生值，不做副作用；`watch` 显式声明源，适合比较新旧值、控制触发时机；`watchEffect` 自动收集其同步执行期间访问的依赖，适合短小、依赖自然变化的副作用。

**边界与取舍**

`await` 之后读取的响应式值不被 `watchEffect` 自动追踪；复杂请求应选 `watch` + 明确 key。

**常见误区**

用 `computed` 发请求；认为 `watchEffect` 会追踪整段异步函数。

**追问**

如何防止搜索框乱序响应覆盖新结果？——清理旧请求或用递增请求号。

## computed 、普通方法和 watchEffect 分别适合什么？

**考察意图**

依赖图与缓存语义。

**核心答案**

`computed` 表达可由响应式输入同步推导的值并按依赖缓存；方法每次渲染都会执行，适合轻量无缓存计算；`watchEffect` 用于执行有副作用的响应式工作，并应让依赖读取清晰、清理资源。异步 `watchEffect` 只自动跟踪首个 `await` 前读取的依赖。

**追问**

为什么一个昂贵列表过滤适合 computed，但服务端搜索不应直接放入它？

**边界/误区**

不把 fetch、随机数或写状态塞进 computed；不要假定 watchEffect 能自动追踪异步回调内后来读取的一切。

**来源/审校**

learning-vue3、现代 JavaScript 教程、Vue 官方；**已准入**。

## watch 的 flush: 'pre' 'post' 'sync' 如何选？

**考察意图**

是否理解副作用时序而不是机械套配置。

**核心答案**

默认 `pre` 在组件 DOM 更新前执行，适合通常的派生副作用；需要读取本组件更新后 DOM 时用 `post`；`sync` 对每次变更立即触发，适合极小、不可批处理的同步约束，滥用会放大频繁变更成本。异步副作用须用 cleanup 取消过期请求。

**追问**

搜索输入变更后如何保证旧请求不能覆盖新结果？

**边界/误区**

`post` 不保证浏览器 paint；`sync` 不是“更快”的默认优化。不要在 watcher 中无条件写回其依赖形成循环。

**来源/审校**

learning-vue3、Interview Handbook、Vue 官方；**已修订**，补齐 paint/cleanup 边界。

## watcher 的异步竞态怎样终止旧请求？

**考察意图**

取消与正确性是否都覆盖。

**核心答案**

每次源变化创建 `AbortController`，在 watcher invalidation cleanup 中 abort；提交前检查 signal/请求序号仍是最新。取消节约资源，但后端可能已经完成，因此写操作还要幂等键和状态查询。loading/error 也按当前 request id 归属，不能由旧请求清空。

**边界与取舍**

debounce 是减少启动数，不能替代取消；缓存命中也必须与当前 key 对齐。**误区：** abort 自动回滚服务端副作用。**追问：** 如何测试“慢旧请求最后返回”不覆盖 UI？

来源：现代 JavaScript 教程、learning-vue3（curated）；Vue docs（primary）。审校：**已准入**，current。

## 哪些 watcher 会自动停止，哪些不会？

**考察意图**

生命周期与内存泄漏。

**核心答案**

在 `setup()` 同步创建并归属组件实例的 watcher 会在卸载时停止；异步回调、计时器或组件外创建的 watcher 可能没有该归属，须保存 stop handle 或纳入 `effectScope` 并显式停止。

**边界与取舍**

停止 watcher 不会撤销已经发生的 I/O；仍要清理订阅、计时器和未完成请求。

**常见误区**

认为任何 `watch()` 都会自动回收。

**追问**

如何写测试？——挂载/卸载后触发 source，断言回调和网络 mock 不再运行。

## 异步 watcher 如何取消过期请求？

**考察意图**

请求竞态与资源释放。

**核心答案**

在回调同步阶段注册 `onWatcherCleanup`（或第三参 `onCleanup`），用 `AbortController` 中止旧 `fetch`；同时只提交最新请求对应的数据，区分 `AbortError` 与真实失败。

**边界与取舍**

清理只能取消支持 signal 的工作；已经提交的写操作要靠幂等键、事务或状态查询，不能声称 abort 会回滚服务端。

**常见误区**

`await` 之后才调用 `onWatcherCleanup`；吞掉所有异常并显示空列表。

**追问**

旧浏览器/非 fetch 客户端怎么办？——使用客户端的取消接口与请求序号兜底。

## KeepAlive 与 Teleport 组合时如何定义可见性和资源存活

**问题**

缓存的评审页把浮层 Teleport 到 body，切换页面后浮层和轮询应怎样处理？

**考察意图**

**核心答案**

**常见误区**

Teleport DOM 仍在就代表组件仍激活；只写 onUnmounted 即可。

## KeepAlive 的停用不等于卸载

**核心答案**

被 KeepAlive 缓存的组件切走时进入 deactivated，实例和状态保留；淘汰或真正卸载时才 unmounted。

需要暂停的订阅、轮询和昂贵观察可在 `onDeactivated` 停止，在 `onActivated` 恢复。

**边界与取舍**

Teleport 只改变 DOM 渲染位置，不改变逻辑父子关系；可见性和资源存活必须单独建模。

**常见误区**

路由切走一定触发 `onUnmounted`，或 Teleport 到 body 后生命周期归 body 管。

## React/Vue 列表中用 Set 去重时有哪些更新陷阱？

**考察意图**

React state 必须产生新 `Set` 后再 `setState`；Vue 中可追踪集合操作，但应避免在派生计算/渲染期间无边界 mutate。列表仍以持久 ID 作为 key；去重规则要明确是 ID、规范化文本还是内容哈希。

`new Set(items)` 只按引用或原始值判断，不能深度去重对象。去重不会替代分页、排序稳定性或服务端幂等。

## Vue/React 中为什么不能仅靠类型避免异步竞态？

**考察意图**

区分静态约束与运行时生命周期。

**核心答案**

类型只能描述 signal、状态和返回值；参数变更、卸载、SSR/hydration 时序仍在运行时发生。为请求设置取消与“仅接收最新响应”的策略，清理 effect/watch；错误 UI 区分取消和失败。近期 Vue SSR watcher 报告说明异步生命周期边界必须以复现和版本文档校验，不能把社区 issue 当普适事实。

**边界与取舍**

有缓存库时遵守其 query key/cancellation 语义，勿叠加冲突的手工状态；有些请求不可取消，仍需结果过期保护。

**常见误区**

认为 `AbortController` 自动阻止所有副作用；把所有 abort 显示为错误 toast。

**追问**

SSR 的 cleanup 在哪里验证？——最小复现、服务端压力/内存测试、框架版本 changelog 和集成测试。

## 为什么 v-for 的稳定 key 同时是正确性和性能问题？

**考察意图**

理解 DOM/组件身份。

**核心答案**

稳定且唯一的 key 让 Vue 将旧节点和同一逻辑实体对应，保留正确的局部状态、焦点与 DOM，并让差异更新更准确。应优先使用数据的持久 ID；排序、插入、删除的动态列表不应以 index 代表身份。

**追问**

以 index 为 key 为什么会让编辑行的输入值“跑到另一行”？

**边界/误区**

key 不会自动优化所有渲染，也不能使用每次 render 都变的随机值；确实没有身份且无状态的静态列表才可能不需要 key。

**来源/审校**

Front-End Checklist、learning-vue3、Vue 官方；**已准入**。
