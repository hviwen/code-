## CI 中如何处理 flaky test 而不掩盖缺陷

**问题**

重试后通过的 E2E 是否应视为绿色？

**考察意图**

工程质量、可观测性、Git bisect 与发布门禁。

**核心答案**

单独标为 flaky，保留首败与重试的 trace、seed、run、浏览器和提交；先复现并定位共享状态、未等待异步、时间/网络依赖。必要时限时 quarantine 且有 owner/期限，但关键安全和数据完整性测试不得靠重试放行。修复提交加入最小回归并用 repeat/bisect 验证。

**边界与取舍**

retry 可收集证据或缓冲极少数基础设施抖动，不是正确性证明；并行/串行差异应作为隔离缺陷调查。

**常见误区**

提高 timeout、无限重试、删掉偶发测试。

**追问**

怎样区分产品竞态与测试框架噪声？

## React Compiler 如何灰度并证明收益

**问题**

大型存量项目怎样引入 React Compiler，而不是全量打开后凭感觉验收？

**考察意图**

Git、工程化、性能与回滚。

**核心答案**

先修 Rules of React；按目录/annotation 小范围启用；单独提交配置与代码修正；建立行为回归、Profiler/真实用户指标和 bundle/build 指标；feature gate/A-B 灰度，异常可快速关停。

**边界与取舍**

Compiler 自动 memoization 不保证每个页面更快；第三方库和手写 memo 需逐步核查，不能盲删。

**常见误区**

构建成功或 render 次数下降就等于用户体验提升。

**追问**

怎样区分编译器收益与同时发生的业务改动？

**快答**

小范围启用、独立提交、行为与性能双门禁、A/B/gating、可快速回滚。

## Release 分支如何回退有依赖的多提交改动

**问题**

TRD 评审样式分三次提交，后一个提交依赖前一个，线上回归如何安全回退？

**考察意图**

提交依赖、revert 顺序、门禁和非代码副作用。

**核心答案**

先画提交/功能依赖并确认已合并拓扑；能关 flag 先隔离；代码按逆依赖顺序 revert，merge commit 明确 mainline；解决冲突后重跑目标页面、历史记录、权限和视觉测试；配置/数据变更有独立回退方案和审计记录。

**边界与取舍**

若后续提交已复用基础能力，整段回退可能扩大影响，应选择补丁或局部 revert；不改写共享 release 历史。

**常见误区**

直接 reset/force-push；只看文件数量决定可独立回退。

**追问**

什么时候 `revert A..B` 的选择范围会漏掉边界提交？

## Revert 是追加反向提交而非抹除历史

**核心答案**

`git revert` 根据既有提交生成反向变化并创建新提交，适合已共享历史。

先识别目标及后续依赖，必要时按逆依赖顺序回退；冲突解决后重新跑门禁。

**边界与取舍**

回退 merge 需要明确 mainline；revert 不自动撤销数据库、配置和外部副作用。

**常见误区**

revert 等价 reset，或回退一个功能提交一定能独立恢复系统。

## 乐观状态是临时投影，不是新的事实源

**核心答案**

`useOptimistic` 在 Action pending 期间将临时更新叠加到当前权威 value 上。

成功后权威 value 收敛，失败后回到当前 value；reducer 可在基线变化时重新计算投影。

**边界与取舍**

服务端仍负责权限、version 与冲突；客户端必须展示 pending/error 并避免重复提交。

**常见误区**

乐观更新成功显示即代表服务端提交成功，或失败时只要把本地布尔值取反即可。

**常见误区**

代码行数减少或构建通过就是性能收益。

## 乐观更新怎样避免双写、乱序和冲突？

**考察意图**

写路径的可恢复性。

**核心答案**

每次 mutation 有稳定 client mutation id 与 idempotency key；本地以可回滚补丁记录前置版本，队列按实体/依赖排序。服务器以幂等键去重并返回权威版本；版本冲突时停止该实体队列、展示差异或走业务合并，不能盲目覆盖。重放成功后确认/失效相关 query。

**边界与取舍**

适合可逆、低风险编辑；库存扣减、支付等高风险操作应以服务端确认状态为准，离线只保存草稿或受控意图。

**常见误区**

`onError` 直接回滚整个 cache，误删后续成功操作。

**追问**

两个标签页同时编辑同一任务时，哪个字段可 LWW，哪个必须冲突提示？

## 乐观状态是临时投影

**核心答案**

`useOptimistic` 在 Action 进行时把待确认动作投影到权威状态之上。

成功后权威 value 前进，失败后临时层消失并回到当前权威值。

**边界与取舍**

仍需幂等键、冲突策略、错误提示与服务端鉴权。

**常见误区**

乐观 UI 等于本地先永久写入。

## Git bisect 如何在测试不稳定时产出可信回归证据

## 如何从格式化噪声中审查真实 Git 变更

**问题**

**核心答案**

- 不要为了清爽重写用户尚未提交的变更。

**追问**

## ETag 如何同时服务缓存验证与并发写保护？

**考察意图**

是否理解版本而不只会背 header。

**核心答案**

**追问**

编辑表单冲突时，为何不能静默覆盖？

**边界/误区**

弱 ETag 不适合所有强一致比较；ETag 不能替代业务幂等键，也不能解决两个合法写入的业务合并。

**来源/审校**

前端内参、MDN；**已准入**。

**核心答案**

更新携带 version/ETag，服务端不匹配返回冲突，客户端提示刷新/合并。

**边界与取舍**

## 自动保存是版本化写协议

**核心答案**

自动保存至少需要 dirty revision、在途请求、成功确认和失败重试四类状态。

保存启动时捕获 revision；只有返回时 revision 未变化才标记 saved，否则保持 dirty，避免旧回包伪装成最新成功。

**边界与取舍**

客户端 revision 只解决本页顺序；多端协作还需服务端 version/ETag、幂等键或冲突协议。

**常见误区**

请求 200 就能清除所有 dirty，或 debounce 能自动保证顺序与不丢数据。
