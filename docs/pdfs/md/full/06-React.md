## React render 是状态快照

**核心答案**

每次 render 读取该次渲染固定的 props/state，事件闭包也捕获该快照。

setter 排队触发后续 render，不会修改当前运行函数里的变量。

**边界与取舍**

需要基于最新状态累计时用函数式 updater；外部可变数据需 `useSyncExternalStore` 等明确订阅契约。

**常见误区**

调用 `setState` 后当前行立刻读到新值。

## React 拖动状态如何避免每个 move 都重渲染

**问题**

React launcher 如何既保持流畅，又让最终位置可声明式恢复？

**考察意图**

state/ref、rAF、闭包和清理。

**核心答案**

影响每帧但不需参与 render 的 latest pointer、起点、rAF id 放 ref；每个 frame 最多提交一次视觉更新，可直接更新受控 CSS 变量/transform或批量 state；拖动结束把最终语义位置写 state/storage。render 内读写 ref 不应破坏纯性。

**边界与取舍**

直接 DOM 更新限定在孤立视觉层，业务/可访问状态仍用 state；高频 setState 是否足够要实测，先保留简单实现。

**常见误区**

ref 变化会自动渲染；每个 move 同步读 layout 再写 style。

**追问**

Strict Mode 与卸载时怎样避免遗留 rAF？

## React 组件测试如何证明迟到回包无效

**问题**

用户先选 PRD A 再选 B，怎样测 A 的迟到响应不会覆盖 B？

**考察意图**

React 可观察行为、可控 Promise 和竞态回归。

**核心答案**

为 A/B 注入可手动 resolve 的 Promise；先触发 A，再触发 B，先完成 B 并断言 B 内容，再完成 A 并断言 UI 仍是 B。通过 role/name 查询与用户操作观察结果，同时断言旧请求被取消是辅助证据，最终状态门禁才是核心。

**边界与取舍**

不要断言 hook 私有 state 或 effect 次数；Strict Mode 下实现细节次数可能不同。

**常见误区**

只测 AbortController 被调用，或用 test id 绑定 DOM 结构。

## Snapshot hotfix 变基后如何证明补丁语义未漂移

**问题**

修复原地 mutation 的补丁从 feature 回迁 release，rebase 后只看最终 diff 够吗？

**考察意图**

最小回归 fixture、commit series、range-diff、cherry-pick 与回滚。

**核心答案**

先把失败时序固化成最小测试；修复与无关格式化分提交；用 `git range-diff` 比较 rebase 前后提交序列，用目标 release 的 focused test/build/真实环境复现验证，再 cherry-pick 或合并。记录基线、版本、commit 和回滚点；回滚使用可审查的 revert，不改写共享历史。

**边界与取舍**

range-diff 比较补丁系列，不证明运行时正确；依赖版本不同需重新安装/锁文件核对。生产回滚不以社区 issue 状态决定。

**常见误区**

只看“tests passed”不保存失败 fixture；把 patch-package 当长期事实源；为干净历史丢掉诊断提交。

**追问**

补丁依赖前置 commit 时如何排序 cherry-pick 和 revert？

## ref 与 reactive 的选择规则是什么？

**考察意图**

代理边界和可维护状态模型。

**核心答案**

原始值、可整体替换的值、跨函数传递的单一状态优先 `ref`；对象集合可用 `reactive`，但重赋值会断开原变量引用。解构 reactive 属性会丢失响应式连接，需 `toRefs`/`toRef`。

**边界与取舍**

第三方类实例、DOM 对象和不可扩展对象不应盲目深代理；可用 `markRaw` 或 `shallowRef` 并自己控制更新点。

**常见误区**

为了少写 `.value` 一律 `reactive`。

**追问**

大图表实例为何常用 `shallowRef`？——避免深层代理，替换实例时才触发更新。

## 原地 mutation 为什么会让订阅者漏更新

**问题**

数组 `push` 后明明有新元素，为什么订阅组件可能不渲染？

**考察意图**

引用相等、结构共享、快照协议与测试不变量。

**核心答案**

若 snapshot 返回同一个数组，React 的 `Object.is(next, previous)` 仍为 true；通知并不等于一定重渲染。更新应产生新快照引用，或 mutable store 用 version 生成并缓存不可变 snapshot。测试同时断言数据、引用变化和订阅次数。

**边界与取舍**

不能机械深拷贝大型 store；按变化路径做结构共享，并让 selector 只订阅必要片段。

**常见误区**

手动 forceRender 掩盖协议错误；用 JSON.stringify 比较全部状态；把社区一行修复直接套到本地。

**追问**

怎样构造一个会让“原地 push + 手动通知”失败的最小测试？

## 为什么连续三次 setCount(count + 1) 只增加一次

**问题**

**快答**

同一 render 快照产生三次相同替换值；累计更新用纯函数 updater。

## React form Action 与原生 requestSubmit 怎样协作

**问题**

自定义提交按钮为什么应优先调用 `requestSubmit(submitter)` 而不是 `form.submit()`？

**考察意图**

HTML 提交算法、submitter、约束验证与 React Action。

**核心答案**

`requestSubmit` 模拟提交按钮，携带 submitter 的 name/value 和 form overrides，执行约束验证并触发 submit；`submit()` 直接进入提交算法，不触发同等验证/事件。React function action 可接收 FormData 并管理 Action pending，但服务端仍重验权限与 schema。

**边界与取舍**

Shadow DOM/form-associated custom element 的 override 仍有标准讨论；不要临时篡改 form action 后忘记恢复。多按钮必须测试每个 submitter。

**常见误区**

button 默认类型总是 button；disabled UI 等于服务端拒绝；客户端通过即可信。

**追问**

如何测试 Enter 提交、不同 formAction 按钮和失败后焦点？

## React 的 'use client' 真正划定什么边界？

**考察意图**

RSC 模块图与 bundle 控制。

**核心答案**

它置于文件顶部，标记该模块及其传递依赖为客户端模块；从 Server Component 导入时形成 server/client 边界。把交互叶子下沉，避免把大布局、数据层和无交互依赖意外送到浏览器。

**边界与取舍**

它不是“这个组件只在浏览器执行”的口号；同一组件定义可因使用位置产生 server/client 不同用法。具体框架打包/渲染细节要以框架文档与构建产物验证。

**常见误区**

在每个交互组件都加指令，或把数据库客户端经 client 边界导入。

**追问**

如何找边界放错？——检查 bundle、序列化报错、网络 waterfall 和依赖图。

## Server Component、SSR 与 Server Function 的关系是什么？

**考察意图**

避免把三个概念混成一个。

**核心答案**

RSC 在独立服务器环境中预渲染，结果可与 Client Component 引用一起传给浏览器；SSR 是生成初始 HTML 的渲染策略，可与 RSC 配合；`'use server'` 标记的是可被客户端发起网络调用的 Server Function，常用于变更，不是“把组件变成服务端组件”的指令。

**边界与取舍**

框架对 RSC bundler API 的支持仍需锁定兼容版本；Server Function 参数完全由客户端控制，必须鉴权、校验、限流并处理重放/幂等。

**常见误区**

用 Server Function 承担常规读请求或把它当安全边界。

**追问**

支付提交怎样设计 idempotency key 与可审计错误码？

## 'use client' 实际划分了什么？

**考察意图**

区分模块依赖图、渲染树与运行环境。

**核心答案**

它标记一个模块及其传递依赖为客户端代码；从服务端模块导入该模块时形成 RSC 边界。不是给每个交互组件都随手加的标签。把状态、事件、浏览器 API 收敛到叶子 Client Component，数据读取和静态展示尽量留在服务端以减小发送和执行的 JS。

**边界与取舍**

Client Component 可接收 Server Component 的 JSX 作为 children；但跨边界 props 必须可序列化。共享纯函数可在两端分别被求值，不能把含密钥或 Node API 的模块混入客户端依赖链。

**常见误区**

“没有指令就一定只在服务器运行”；组件使用位置和依赖图共同决定运行环境。

**追问**

如何通过 bundle 分析证明边界优化确实减少了首屏 JS？

## useOptimistic 如何处理失败、乱序与重复提交

**问题**

评审“通过/拒绝”怎样做乐观 UI 又不掩盖服务端失败？

**考察意图**

React Action、状态机、幂等与安全。

**核心答案**

乐观层记录 clientMutationId、目标动作和 pending；服务端以幂等键/版本校验落权威结果；成功用服务端实体收敛，失败回退并可重试，迟到响应按版本忽略。

**边界与取舍**

**追问**

**快答**

临时投影 + mutation ID + 服务端幂等/版本 + 成功收敛/失败回退/迟到忽略。

## useOptimistic 如何处理服务端版本冲突与失败回滚

**问题**

检查项从 unresolved 乐观改为 resolved，服务端返回 409 时怎么办？

**考察意图**

权威状态、reducer、幂等、冲突与错误呈现。

**核心答案**

以服务器返回的 entity/version 为基线；Action 内派发带 operationId 的 optimistic action；服务端校验主体/对象/version。成功用新权威状态收敛，409 拉取或采用响应中的最新快照并提示冲突，失败保留可重试信息。父聚合由领域规则重算，不由卡片局部取反。

**边界与取舍**

高风险操作可不用乐观更新；多字段相关变化用纯 reducer 保持一致。重试必须幂等并防重复提交。

**常见误区**

保存一个“旧布尔值”失败时直接恢复；忽略其他协作者已产生的新版本。

**追问**

两个 optimistic operation 交错失败时如何按 operationId 对账？

## useSyncExternalStore 的 subscribe 与 getSnapshot 契约是什么

**问题**

为什么 store 未变化时 `getSnapshot` 必须返回同一值？

**考察意图**

外部状态、并发一致性、订阅清理、SSR。

**核心答案**

`subscribe` 注册 change callback 并返回 unsubscribe；`getSnapshot` 只返回 render 所需的不可变快照，未变化时保持 `Object.is` 相等，变化时换引用。SSR 提供与客户端首帧一致的 `getServerSnapshot`。subscribe 函数身份应稳定，组件卸载必须清理。

**边界与取舍**

通常由 store/library owner 封装，业务组件只消费 selector；mutable store 需 version/cache。外部 store 在 Transition 期间变化时 React 可能转为阻塞重试以避免 tearing。

**常见误区**

每次构造新对象、组件内新建 subscribe、在 getSnapshot 中写状态或发请求。

**追问**

怎样证明快速切 scope 时旧订阅不会污染新快照？
