## lockfile 是解析快照

**核心答案**

它记录具体版本、完整性与依赖图；大 diff 不等于每行都有业务意义。

**边界与取舍**

不同 pnpm 版本可重写格式，需钉住包管理器。

**常见误区**

手工删冲突块就完成修复。

## lockfile 是解析结果快照

**核心答案**

记录依赖解析结果、peer 组合与完整性信息。

安装器结合 manifest、配置、工具版本和 lockfile 构造依赖图。

**边界与取舍**

不同 pnpm 主版本可能迁移格式或改变解析语义；单有 lockfile 不足以保证一致。

**常见误区**

大 diff 一定代表所有依赖升级；正确做法是比较解析结果。

## peerDependency 决定宿主兼容区间

**核心答案**

插件包依赖宿主提供的同一框架实例/版本；不一致可能产生缺失导出或重复实例。

**边界与取舍**

override 是约束修复，不应掩盖真实不兼容。

**常见误区**

只升级报错包，不查消费者。

## pnpm lockfile 升级如何保证可复现构建

**问题**

项目把 pnpm 7 升到 10，lockfile 从 5.4 改为 9.0 且产生上万行 diff。如何判断它是格式迁移还是依赖语义变化，并安全上线？考察依赖解析、CI 一致性和风险隔离。

**核心答案**

先把“包管理器升级”和“依赖升级”拆开。固定 packageManager 与 CI pnpm 版本，在干净环境仅生成 lockfile；比较直接依赖 specifier、解析版本、peer 组合、patch 哈希、registry/tarball 与 install scripts 是否变化。随后执行 frozen lockfile 安装、类型检查、测试、构建和关键运行回归。lockfile 必须与 manifest 同提交，CI 不允许静默重写。

**追问**

如何验证 peer dependency 组合没有漂移？patch 哈希变化为什么属于高风险？CI 缓存键应该包含哪些输入？

**边界、取舍与误区**

- lockfile 大 diff 不等于依赖一定升级，也不等于“只有格式变化”；必须比较解析结果。
- lockfile-only 减少副作用，但仍可能联网和迁移元数据，不替代验证。
- 不要把包管理器迁移、业务功能和批量格式化混在一个提交。
- 当前 pnpm 文档说明 CI 会使用 frozen-lockfile；版本不兼容可能直接失败。

## Git 如何让类型重构可审查、可回滚？

**考察意图**

工程协作，不是背命令。

**核心答案**

把“新增契约/adapter、迁移调用方、删除旧路径”拆为可构建提交；每步带类型检查和关键行为测试。PR 写清兼容窗口与回滚方式；用 feature flag 或双读比对降低风险。冲突先理解语义再解决，禁止把 generated lockfile 或冲突标记当作修复。

**边界与取舍**

小提交不等于碎提交：每个提交都应可说明与尽量可运行；公共分支避免改写历史，按团队规则 squash/rebase。

**常见误区**

只凭 `tsc` 通过就认为迁移成功；将 `git reset --hard` 作为冲突解决方案。

**追问**

怎样回滚数据库/接口已升级的客户端？——先保持向后兼容，再删除旧协议；回滚是发布和数据策略，不只是 Git 操作。

## 乐观更新怎样做到可回滚？

**考察意图**

并发 mutation 的状态建模。

**核心答案**

生成 `mutationId`，记录前态和目标版本，立即展示临时值；响应成功以服务端快照确认；失败仅在该 mutation 仍是当前写入时回滚。并发写入冲突时失效重取或基于版本重放，不能无条件恢复旧对象。

**常见误区**

失败后把整个列表替换为旧快照，覆盖后续成功操作。

**追问**

服务端已写成功但响应丢失？——以幂等键查询/重试，服务端返回首次结果。

**伪代码**

`const undo = applyOptimistic(id, patch, mutationId); try { confirm(await save({id, patch, version, mutationId})) } catch { undoIfCurrent(mutationId) }`

## 乐观标题更新必须可回滚

**核心答案**

先更新侧栏可降低等待感，但失败时要恢复旧值并显示错误。

**边界与取舍**

多人改名或跨标签页需版本/时间戳处理冲突。

**常见误区**

失败只打印 console。

## 取消终态

**核心答案**

response.cancelled 应结束 loading、阻止自动 resume 并保留可重试上下文。

**边界与取舍**

取消不自动回滚已写文档。

**常见误区**

连接断开即等于用户取消。

## CSS :empty 为什么不能判断编辑器正文为空

**问题**

为什么 `.ProseMirror:empty` 不能成为保存按钮和 placeholder 的统一事实源？

**考察意图**

DOM 节点、CSS selector、编辑器 decoration 与领域状态分层。

**核心答案**

`:empty` 只匹配没有 element/text children 的元素；空段落、`
`、空白文本或 node view 都会让它不匹配。CSS 只负责呈现，保存应依赖编辑器文档模型的领域谓词；placeholder 可用编辑器提供的 empty state/data attribute 渲染，但不能反向驱动持久化。

**边界与取舍**

纯静态表单可用 `:placeholder-shown`/`:empty` 做视觉提示；富文本必须覆盖 schema、atom node 和跨浏览器 DOM 差异。

**常见误区**

把 `display:none` 当数据删除；通过 class `is-empty` 推断后端正文为空。

**追问**

空态样式与屏幕阅读器提示怎样避免只靠颜色或伪元素？

## Vue watcher 自动保存如何避免旧回包与泄漏

**问题**

Vue 中正文变化后 debounce 保存，路由切换或下一次变更发生时怎样取消旧副作用并保持 dirty 正确？

**考察意图**

watch cleanup、同步注册、revision、AbortController 和卸载。

**核心答案**

watch 只监听必要 revision/序列化结果；回调同步创建 timer/controller 并立刻注册 `onCleanup`，清 timer/abort 旧请求。请求携带 revision/version，只有最新成功才置 saved，失败保持 dirty。`onWatcherCleanup` 在 Vue 3.5+ 且必须在首次 await 前同步调用；兼容版本用回调第三参 `onCleanup`。

**边界与取舍**

watcher 停止不等于已发服务端写入可撤销；写操作仍需幂等和冲突控制。大 JSON 深监听可能昂贵，优先编辑器 update/revision。

**常见误区**

await 后调用 `onWatcherCleanup`；每次变化并行发写请求；finally 无条件清 dirty。

**追问**

AI 写入、手工编辑和远端 refresh 同时发生时怎样定义优先级？

## pagehide 与 sendBeacon 能否保证离场保存

**问题**

把最终正文只放在 `pagehide` 中用 `sendBeacon` 保存，是否可靠？

**考察意图**

页面生命周期、传输限制、确认语义和恢复。

**核心答案**

不可靠。移动端可能不触发 pagehide；beacon 只支持 POST、小数据且 true 仅表示进入发送队列。主路径应持续增量保存并有服务端版本确认；`visibilitychange`/`pagehide` 只发送小型、幂等的 dirty/revision 提示或最后增量，下一次打开再对账恢复。

**边界与取舍**

需要自定义 method/header/读取响应时可考虑 `fetch(...,{keepalive:true})`，仍不可承诺完成。大正文应提前分片或常态保存。

**常见误区**

在 unload 阻塞导航；beacon 传完整富文本和敏感数据；返回 true 立即显示“已保存”。

**追问**

客户端崩溃、断网和 bfcache 恢复分别怎样验证？

## contenteditable 与编辑锁怎样组成一致权限边界

**问题**

**考察意图**

HTML 枚举属性、UI/服务端授权、编辑器命令与粘贴输入。

**核心答案**

不足。`contenteditable` 是 UI 编辑能力，不是安全边界；只读态还要禁用编辑器 commands、自动保存、AI 写入、快捷键/拖拽/粘贴入口，服务端按用户与 editSession/version 校验写权限。属性是 enumerated，不是普通 Boolean；嵌套可编辑区和 node view 需单独验证。

**边界与取舍**

只读仍可允许选择/复制/评论；可访问状态需清楚提示锁拥有者和恢复路径。RN/uni-app 不应假设同一 DOM 行为。

**常见误区**

`:disabled` 样式等于后端拒写；字符串 `contenteditable="false"` 被框架错误当 truthy；隐藏保存按钮但 API 仍可调用。

## 怎样定义结构化编辑器的有效正文

**问题**

`{type:'doc',content:[{type:'paragraph'}]}`、空 HTML、图片节点和业务卡片分别应如何判断是否可保存？

**考察意图**

领域谓词、递归树、trust boundary 和无文本节点。

**核心答案**

先拒绝 null、数组和无 type 对象；字符串先 trim，JSON 字符串解析后递归，HTML 用 DOMParser 读取文本并白名单检查媒体/业务节点；JSON 中 text 节点要求非空文本，容器递归 children，允许的 atom/业务节点即使无 text 仍可算正文。谓词服务于保存门禁，不等于 schema 校验或 XSS 清洗。

**边界与取舍**

未知 node 不应一律当有效正文；应按当前 schema/迁移表决定 reject、隔离或兼容。附件占位、失败卡片是否算正文由产品定义。

**常见误区**

只看 `textContent`，会误杀图片/mention/card；只看对象 truthy，会把默认空段落当正文。

**追问**

如何让前端、后端、AI refresh 和导入任务共享同一组 fixture？
