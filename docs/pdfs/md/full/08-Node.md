## Node Writable.write 返回 false 后该做什么

**问题**

转发 AI token 时 `res.write(chunk)` 返回 false 表示什么？

**考察意图**

Node 背压、内存与慢客户端。

**核心答案**

chunk 已被接收进缓冲，但缓冲达到阈值；生产者应暂停读取/生成，等待 `drain` 再继续。优先使用 `pipeline()` 让错误、关闭和背压统一传播。

**边界与取舍**

`drain` 只代表缓冲可继续写，不代表客户端业务已处理。

**常见误区**

false 表示写失败并应立即重试同一 chunk；或无视 false 继续写。

**追问**

数千慢连接怎样限制总内存？

## Node events.once() 为什么可能漏事件？

**考察意图**

EventEmitter 同步发射与 await 续体交错。

**核心答案**

`emit` 同步调用监听器。若连续 `await once('a')` 再创建 `'b'` 监听，而两事件都在同一轮/`nextTick` 发出，Promise 续体未运行，第二个监听尚不存在，`b` 就会丢。应先创建两个 Promise，再 `await Promise.all`。

**追问**

流式协议如何用序号/缓冲防止短暂离线丢消息？

**边界/误区**

不是浏览器 EventTarget 的通用结论；不要以为 async listener 会让 emit 等待。

Node.js Best Practices、Node docs；**已准入**。

## 背压是生产者与消费者的流量协议

**核心答案**

消费者处理不过来时，生产者降低或暂停产生速度。

Node stream 的 `write()` 返回 false 后等待 `drain`；`pipe`/`pipeline` 协调错误与节奏。

**边界与取舍**

`highWaterMark` 是阈值而非硬内存上限，总预算还含 socket、解析、队列和并发流。

**常见误区**

调大 highWaterMark 等于性能优化，或内存绝不会超过该值。

## 背压是生产者服从消费者速度

**核心答案**

消费者变慢时，生产链暂停/减速，避免无界缓冲。

Node Writable `write()` 返回 false 后等待 `drain`；pipe/pipeline 自动协调。

**边界与取舍**

背压不等于业务限流，也不自动限制所有用户总内存。

**常见误区**

流式传输天然不占内存。

# 取消与超时

## AbortSignal 是一次性取消状态

**核心答案**

signal 从未取消单向进入已取消，并携带 `reason`。

消费者检查 `aborted`/`throwIfAborted()`，或监听一次 `abort`；组合信号表达“任一上游取消”。

**边界与取舍**

取消是协作协议，不会神奇终止任意 CPU 代码；复用已取消 signal 会立即失败。

**常见误区**

AbortController 可 reset，或触发 abort 就证明 socket、定时器、流都已释放。

## BFF 如何做超时、降级和部分成功？

**考察意图**

面向前端体验设计后端聚合。

**核心答案**

对每个依赖设预算、超时和取消传播，隔离慢依赖；可独立展示的数据并行聚合，失败项按 UI 契约返回可识别状态（`available | unavailable | stale`），而非整页 500。缓存需带版本/TTL 和权限维度，trace ID 贯通。

**常见误区**

无限重试或静默吞错显示空数据。

**追问**

什么时候宁可失败？——支付、权限等强一致关键路径不可用陈旧值掩盖。

## Node fetch 收到 headers 后取消时还要考虑什么

**问题**

fetch 已返回 Response，读取大 body 中途取消，哪些资源和错误路径仍要验证？

**考察意图**

headers/body 两阶段、Undici、连接复用和迟到数据。

**核心答案**

fetch fulfillment 只表示 headers 可用，body 仍是异步流。读取阶段继续传递/遵守 signal，取消后确认 reader/body 被取消或消费、错误被观察、业务状态不再提交，并通过活跃句柄、连接池和内存指标验证释放。不能由一次 reject 推断 socket 状态。

**边界与取舍**

小响应可一次性解析；大响应优先流式处理和预算。特定 HTTP/2 竞态须锁 Node/Undici/平台版本复现。

**常见误区**

Response 到达等于下载完成；abort 后忽略 body；从关闭 issue 推断所有版本都无风险。

**追问**

如何构造 headers 已到、body 慢速分片、取消与迟到 chunk 的测试？

## Node 服务如何把超时、客户端断连与主动取消统一到 AbortSignal ？

**考察意图**

是否能避免无效下游工作与取消误报。

**核心答案**

每个请求建立/继承 signal；把客户端断连、业务 deadline 和上游取消组合后传入 `fetch`、DB/SDK（仅限其明确支持时）。监听取消后停止下游工作并释放资源；将已知取消分类为 cancelled/499 类观测，不与 5xx 混算。下游不支持 signal 时使用它自己的取消 API 或显式设超时，不能假装已取消。

**边界与取舍**

取消是协作协议，不能撤销已提交的数据库写；写操作需幂等键、事务或补偿。不要在每层新建 controller 而丢失父级取消。

**常见误区**

捕获所有错误后返回空数组；超时后继续重试非幂等写；把 abort 当成功。

**追问**

页面刷新时怎样处理？——前端取消展示需求；服务端是否继续执行由业务 SLA 决定，关键写入需独立任务与状态查询。

## Promise.race 超时为什么可能留下后台工作

**问题**

`Promise.race([fetch(), timeout])` 已 reject，为什么进程仍可能占 socket 或最终产生副作用？

**考察意图**

Promise 结算与底层取消分离。

**核心答案**

race 只采用最先结算的结果，不会取消输掉的 Promise。应让操作接受 signal，超时时 abort，并在 finally 清定时器；非可取消 SDK 需用其取消接口、隔离 worker 或限制并发，不能宣称已停止。

**边界与取舍**

已发送的服务端写入未必可撤销，需幂等键、状态查询或补偿；客户端 abort 不是事务回滚。

**常见误区**

忽略迟到 rejection；超时后自动重试非幂等请求；把 UI 停止 loading 当资源释放证据。

**追问**

服务端已接收写请求时，怎样避免重试造成双写？

## React、Vue 请求生命周期如何跨 Web、RN、uni-app 建模

**问题**

如何共享请求状态机，同时避免假设三端 AbortSignal/stream 行为一致？

**考察意图**

领域不变量、平台能力矩阵与卸载清理。

**核心答案**

## 如何把取消从浏览器传到 Node 下游

客户端 abort，BFF 感知断开并逐跳传 signal；已提交副作用另用幂等/补偿。

## packageManager、Corepack 与 CI 版本钉住

**问题**

为什么只提交 pnpm-lock.yaml 还不足以保证团队和 CI 安装一致？

**核心答案**

lockfile 格式与解析语义受 pnpm 主版本影响。packageManager 用来声明项目期望的工具和版本；本地与 CI 应读取同一声明，安装时使用 frozen lockfile。Corepack 是可选的版本分发方式，不是唯一方案；当前 pnpm CI 文档更推荐直接安装 pnpm，以避免每次命令经过 Node shim 的额外成本。

**边界与取舍**

- engines.node 约束 Node，不等于约束 pnpm。
- 全局 pnpm 恰好可运行，不代表与项目声明兼容。
- 固定版本不替代 lockfile，也不替代供应链和安装脚本审查。

**追问**

如何处理开发机离线？为什么 CI 缓存只能由可信任务写入？

## 未知进度为什么不能伪造成百分比

**问题**

没有总字节或总任务数时，进度条为什么不能用定时器走到 90%？

**考察意图**

HTML 语义、可访问性与诚实反馈。

**核心答案**

无总量时用 `<progress>` 不设置 `value` 表达 indeterminate，并给可读标签/状态；有可验证分子分母时再设置 value/max。超时、取消、失败分别呈现，不能让视觉估算冒充事实。

**边界与取舍**

阶段型流程可显示已完成阶段，但不要转换成虚假连续百分比；高频更新要节流并避免 live region 噪声。

**常见误区**
