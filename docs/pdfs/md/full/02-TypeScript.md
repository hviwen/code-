## API 响应为什么先接成 unknown

**问题**

PRD 评审详情接口已有 `ReviewDetail`，为什么边界仍应从 `unknown` 开始？

**考察意图**

TS 静态边界、运行时校验与信任模型。

**核心答案**

类型声明只约束本地编译；网络值可能因版本、代理、权限或异常格式偏离。边界把 JSON 视为 `unknown`，校验 discriminant、必填字段、数组元素和约束，再返回领域类型；失败映射为可观测的 contract error。

**边界与取舍**

小型内部接口可手写 guard；复杂/复用 schema 可用已安装验证库，但要锁版本、测 coercion/strict 行为，避免双份类型漂移。

**常见误区**

`as ReviewDetail`、泛型 `fetch<ReviewDetail>` 能验证响应。

**追问**

如何避免 schema 与 TypeScript type 双向漂移？

## 为什么 API 响应入口应是 unknown 而非断言类型？

**考察意图**

区分静态类型与不可信输入。**答案：** HTTP JSON、存储和第三方 SDK 都可能违约；入口用 `unknown`，经判别函数/schema 验证后映射领域类型，失败走脱敏错误与降级。`as User` 不产生校验。**边界：** 内部受控函数可用声明；跨进程边界仍校验。**误区：** TS 通过就不会收到坏数据。**追问：** 如何处理未知枚举？**审校：** 已准入，TS primary。

## TypeScript 如何让 Map.get() 的 undefined 边界可见？

**考察意图**

类型与运行时事实一致。

**核心答案**

`get` 返回 `V | undefined`，即使 `has` 后也应在同一控制流中收窄，或封装一个遇到缺失即抛出领域错误的 `requireValue`。若 `undefined` 是合法值，不能只靠 `get(...) === undefined` 判断存在性，需配合 `has` 或用显式 discriminated value。

**追问**

当本地缓存被版本迁移清空时，`requireValue` 的错误如何转化为可恢复 UI？

**边界/误区**

非空断言不是校验；不要把用户输入强转成 union key 后就假定字典完整。

**来源/审校**

Front End Interview Handbook、现代 JavaScript 教程、TypeScript handbook；**已准入**。

## TypeScript 类型在运行时会被擦除

**核心答案**

interface、type annotation 和大多数类型操作只服务编译期，生成 JavaScript 后不检查网络数据。

编译器验证已知程序表达式；来自 `fetch().json()`、storage、postMessage、MCP/AI 的值仍需运行时解析。

**边界与取舍**

类型能约束调用者和内部代码，但不能证明服务端响应、权限或数据库事实。

**常见误区**

写了 `response.json() as Review` 就完成了数据校验。

## satisfies 与类型注解/断言分别解决什么问题？

**考察意图**

是否会在配置对象中保留推断信息并拦截拼写错误。

**核心答案**

类型注解把表达式按目标类型检查且可能扩大推断；`satisfies` 检查表达式满足目标约束，同时尽可能保留对象自身的窄类型；断言会要求编译器相信你，不能验证。配置表适合 `satisfies Record<Key, Value>`。

**边界与取舍**

`satisfies` 不做运行时验证，不能替代 schema；目标类型的索引签名可能允许额外字段，要按需要收紧 key。

**常见误区**

以为 `satisfies` 会把值转换为目标类型，或以为能拒绝所有动态额外字段。

**追问**

为什么表项 `timeout: 3000` 有时不能保留字面量？——看推断上下文和 `as const`，并避免为保留字面量牺牲可变性语义。

## unknown 、 any 与类型断言如何在 API 边界分工？

**考察意图**

类型安全是否落在不可信输入的正确位置。

**核心答案**

外部 JSON、catch 值和跨进程数据先当 `unknown`；用运行时 schema/守卫验证并转为领域模型。`any` 会关闭检查，只应在隔离的兼容层短暂使用；`as` 是开发者声明，不会检查或转换值，不能替代验证。

**边界与取舍**

内部可信、已验证的数据可用精确类型；schema 带来代码与运行时成本，但网络边界通常值得。记录验证失败时勿上报原始敏感 payload。

**常见误区**

“接口标了 `User`，响应就是 User”；“`catch (e)` 可直接读 `e.message`”。

**追问**

如何把后端 `snake_case`、日期字符串与可选字段变成前端模型？——在 adapter 做解析、默认/失败策略与字段转换。

## unknown 是安全顶层类型

**核心答案**

任何值可赋给 unknown，但使用前必须缩窄；any 会绕过检查。

**边界与取舍**

断言不是验证，网络边界仍需运行时校验。

**常见误区**

把 unknown 立即 as 成目标类型。

## unknown 要求先证明再使用

**核心答案**

`unknown` 可接收任意值，但在 narrowing 前不能随意访问；`any` 会关闭多数检查。

用 `typeof`、`Array.isArray`、`in`、用户定义 type guard 或 schema parser 将值收窄。

**边界与取舍**

错误的 type predicate 仍会欺骗编译器；guard 本身必须测试异常、缺字段和原型边界。

**常见误区**

`unknown` 与 `any` 只是写法不同，或一次 `as` 就等价于检查。

## 异步页面状态为何用判别联合

**问题**

为什么不用 `loading/data/error` 三个可选字段表示评审页状态？

**考察意图**

TS 状态建模、不变量和 exhaustiveness。

**核心答案**

三个独立字段可形成 loading+data+error 等非法组合；用 `{status:'idle'|'loading'|'success'|'error'}` 判别联合，把每态合法字段绑定，并在 switch 用 `never` 穷尽检查。请求版本/ID 应作为状态的一部分抵御迟到回包。

**边界与取舍**

状态爆炸时可把服务器缓存状态与局部 UI 状态分离；不要为每个布尔量都造一层抽象。

**常见误区**

联合类型会自动处理请求竞态，或 optional 字段加 `!` 就安全。

**追问**

stale data + refreshing 如何建模？

## 条件类型何时分发，为什么 T extends U 会改变结果？

**考察意图**

泛型工具类型是否可解释、可维护。

**核心答案**

当条件左侧是裸类型参数 `T` 时，联合类型会逐成员分发：`T extends U ? X : Y`。包成元组 `[T] extends [U]` 后测试的是整个联合是否可赋值给 `U`，不再分发。先写输入/输出类型测试，再决定是否需要这种能力。

**边界与取舍**

`any`、`never`、`unknown` 的行为不直觉；复杂递归/分发类型会拖慢 `tsc` 和 IDE，应优先命名中间类型、限制递归或换运行时校验。

**常见误区**

把 `extends` 一律解释为继承；用条件类型模拟精确对象类型。

**追问**

如何证明不是“类型体操”？——说明被消除的重复、类型测试、编译诊断和更简单替代方案。

## 组件 API 如何避免“布尔参数爆炸”？

**考察意图**

组件边界、类型与可维护性。

**核心答案**

先识别变体是否仍共享语义与交互。少量互斥变体用受限 union（如 `variant: 'primary' | 'danger'`）；复杂区域用 slots/children 或组合组件；跨领域职责拆为更小组件。为受控/非受控模式定义单一数据源、默认值与回调语义。

**边界与取舍**

不是所有布尔都要删除；独立、正交且语义明确的开关可保留。避免为未来猜测建立“万能组件”。

**常见误区**

用几十个 optional prop 代替组件组合；受控与内部状态双写。

## TypeScript 如何写可演进的事件契约？

**考察意图**

类型边界与演进能力。

```ts
type TaskEvent =
  | { type: 'task.updated'; schemaVersion: 1; eventId: string; taskId: string; version: number; patch: { title?: string } }
  | { type: 'task.deleted'; schemaVersion: 1; eventId: string; taskId: string; version: number };

function apply(e: TaskEvent) {
  switch (e.type) { case 'task.updated': return e.patch; case 'task.deleted': return null; }
}
```

**核心答案**

判别联合让消费者穷尽处理；新增字段可选、未知 `type` 记录并安全忽略或触发升级；边界处以 Zod/JSON Schema 等运行时校验。

## 用户名等异步校验如何避免乱序响应覆盖？

**考察意图**

JS 并发、取消与状态机。

**核心答案**

为每次输入生成版本号或使用 `AbortController` 取消上一请求；仅当响应仍对应当前值/版本时写入结果。对输入做 debounce，并把 `idle → checking → valid/invalid → submit` 状态显式建模。服务端提交时仍要重新判定可用性。

**边界与取舍**

abort 只是尽力终止 I/O，已到达服务端的请求可能仍执行；服务端也要限流、防枚举和审计。不要把“正在校验”误当作“已通过”。

**常见误区**

任一响应返回就更新 UI；仅靠 debounce 解决竞态。

**追问**

网络失败、超时和用户名被占用应如何区分给用户？

## 运行时 schema 如何处理版本漂移与 coercion

**问题**

接口新增字段、缺字段或把数字发成字符串时，parser 应严格拒绝还是自动转换？

**考察意图**

兼容策略、数据安全和演进。

**核心答案**

按方向区分：读取响应通常允许未知新增字段但严格校验已消费字段；写请求使用 allowlist，拒绝未授权字段；coercion 只对明确、可逆、无歧义值开放，并保留原始错误上下文。schema/version 与 fixture/契约测试一起演进。

**边界与取舍**

strict 可早暴露漂移但降低向前兼容；passthrough 不能让未知字段进入领域/日志；日期、大整数、空串/0/false 尤需显式规则。

**常见误区**

开启 coercion 能自动修复所有后端不一致。

## TypeScript 构建变慢怎么排查？

**考察意图**

工程化诊断。

**核心答案**

先收集 `--extendedDiagnostics`/trace、项目引用和依赖图；定位大 `.d.ts`、复杂条件/递归类型、循环引用和无边界的包含范围。以 project references 分割，分离 emit 与类型检查，减少不必要的全量检查；升级编译器必须回归类型错误、产物和 IDE 体验。

**常见误区**

直接关掉 `strict` 或跳过所有库检查来“优化”。

**追问**

CI 与本地不同？——固定 Node/锁文件/缓存键，分别量化冷、热构建。

## TypeScript 编译变慢时怎么定位并做最小改动？

**考察意图**

类型系统与工程性能的真实诊断能力。

**核心答案**

先记录 `tsc --extendedDiagnostics`、受影响 package 和 IDE 症状；比较提交，检查宽泛 include、巨大声明、递归/分发条件类型和循环依赖。用 project references/分包限制范围，简化公共类型与生成声明；每次改动验证错误集、产物及编辑器体验。

**边界与取舍**

不要通过 `skipLibCheck` 或 `any` 直接掩盖自身类型错误；它们可作为有记录的过渡措施但需设到期回收。

**常见误区**

盲目升级 TS；只用一次冷启动时间判断。

**追问**

如何设 CI？——设基线与趋势/预算，区分增量、全量和类型测试，不把偶发机器噪声当回归。
