## contain 与 content-visibility 的收益和风险？

**考察意图**

渲染隔离的语义边界。

**核心答案**

对独立子树用 containment 限制影响；长列表离屏内容可试 `content-visibility:auto` 并给 `contain-intrinsic-size`，降低首次渲染和滚动跳动。

**边界/误区**

`layout`/`paint` 会创建包含块和堆叠上下文，可能改变 fixed、z-index、overflow；不能全局启用而不做视觉/焦点回归。

## content-visibility: auto 适合解决什么问题？

**考察意图**

CSS containment 的收益和行为边界。

**核心答案**

适合长列表、信息流等屏外独立内容：浏览器可跳过暂不相关子树的渲染工作。为减少占位尺寸变化，配合合理的 `contain-intrinsic-size`；通过滚动、焦点、查找与屏幕阅读器实测验证体验。

**边界与取舍**

它不是虚拟列表替代品，也不能修复数据量、图片解码或脚本长任务；带 `contain: size` 时未提供内在尺寸可能得到错误占位。`hidden` 与 `auto` 的可搜索/可聚焦行为不同。

**常见误区**

认为它等于 `display:none` 或可无条件套在任意容器。

**追问**

为什么 `contain: paint` 可能裁剪溢出内容？

## will-change 是否应随处添加？

**考察意图**

图层与内存成本。

**核心答案**

仅在短时、可预测动画前后按需提示，并在结束后移除；先由 trace 证明瓶颈。它可增加内存/合成负担。

**修订**

原“统一 `will-change: transform` 即可加速”过度承诺，改为证据驱动的短生命周期使用。

## content-visibility 跳过离屏工作

**核心答案**

auto 可延迟离屏元素的布局与绘制，同时保留可访问性树语义。

**边界与取舍**

需要 contain-intrinsic-size 避免尺寸跳动，且兼容性要验证。

**常见误区**

它等同于 display: none。

## 怎样确定一个交互该放在哪一侧？

**考察意图**

能否做以用户路径为中心的模块边界。

**核心答案**

先列出交互、状态生命周期、数据敏感度和网络依赖：无交互、可近数据层执行的读取/格式化放服务端；需要 state、effect、事件、DOM 或原生能力的最小岛放客户端。服务端只传 UI 所需 DTO，不传 ORM 实体或机密字段；客户端 mutation 后以明确失效/重新验证策略同步。

**边界与取舍**

“全部 server”会损失离线与即时交互；“全部 client”易产生请求瀑布和大 bundle。用 RUM 的 LCP/INP、bundle 和失败率验证，而非按目录名判断。

**常见误区**

把 database client、环境变量或权限判断导入 `'use client'` 子树。

**追问**

富文本编辑器为何通常是 Client island，首屏文档为何仍可 server-render？

## PWA/React Native 离线恢复的启动顺序如何设计？

**考察意图**

识别 hydration 竞态。

**核心答案**

启动时先恢复安全存储的会话与版本化本地库，再恢复查询快照和操作队列；在恢复完成前显示可解释的 loading/只读壳，避免首屏请求或写入覆盖未恢复状态。恢复后检查 schema、最大保存期、租户和权限，再根据连通性受控刷新与重放。

**边界与取舍**

localStorage 同步但容量/敏感性有限；RN AsyncStorage/IndexedDB 通常异步，必须显式 gate。社区已有“第二次离线重载丢缓存”案例，故必须写重启、离线、恢复失败三类 E2E 测试。

**常见误区**

等待所有网络刷新再可用，或只测试一次 reload。

**追问**

恢复耗时超过性能预算时，哪些界面可先使用只读快照？

## 拖动位置如何跨 Web、RN、uni-app 安全恢复

**考察意图**

**核心答案**

**常见误区**

**边界/误区**

INP 不能单独给根因；单次 Lighthouse 不是现场体验全貌。

## 前端如何把性能预算放进 CI，而不是靠手工截图？

**考察意图**

工程化、可观测性与发布治理。

**核心答案**

对关键路由和设备档位定义预算（如 LCP/INP/CLS、JS 体积、图片体积），在可重复的 lab 测试中采集趋势；PR 对超阈值给出失败或豁免原因。上线后用 RUM 按路由、设备、网络分位数验证，并用 feature flag/回滚策略处理回归。

**边界与取舍**

lab 不能替代 RUM；预算是门槛而非唯一质量指标，要防止测试环境、缓存和数据样本造成假信号。

**常见误区**

只看平均值；只压缩 bundle 而不看关键路径。

**追问**

CI 指标抖动时怎样制定可解释的豁免？

## 图片与字体如何减少 CLS，又不牺牲首屏？

**考察意图**

资源优先级、布局稳定性。

**核心答案**

对图片/广告/嵌入内容预留可预测尺寸或 `aspect-ratio`；响应式图片提供合适的 `srcset`/`sizes`；只预加载经证实的关键资源。字体定义合理 fallback 与 `font-display` 策略，测量替换导致的偏移，关键文案必要时做度量匹配。

**边界与取舍**

预加载过多会竞争带宽；`font-display: swap` 可能改善文本可见性但引入字体替换偏移，需结合字体与真实网络选择。

**常见误区**

一律 preload 全部字体；把懒加载用于首屏 LCP 图。

**追问**

怎样验证某个布局偏移的归因？

## 如何建立可信的 Vue 性能证据，而不是凭体感优化？

**考察意图**

指标、归因和实验设计。

**核心答案**

先定义用户路径和预算，分别测初始加载（如 LCP）和交互更新（如 INP/任务耗时）。在生产样本使用 RUM，在本地/预发用 Chrome Performance 和 Vue performance markers 定位组件更新；一次只改变一个假设，记录设备、网络、数据量和前后分位数。

**追问**

你如何证明虚拟列表改善了输入响应，而不只是减少了节点数？

**边界/误区**

开发模式、DevTools、热更新和单台高性能机器会扭曲结果；不要将某次 flame chart 的“自耗时”直接归因给业务函数。

**来源/审校**

Front-End Checklist、ExplainThis、Vue performance/MDN；**已修订**，修正“FPS 高就是性能好”。
