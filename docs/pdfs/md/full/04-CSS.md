## Flex 与 Grid 的选择标准是什么？

**考察意图**

布局模型和响应式推理。

**核心答案**

一维的内容分布、对齐或工具栏优先 Flex；同时控制行与列、卡片矩阵或明确网格轨道优先 Grid。先让内容决定高度，必要时用 `minmax()`、`auto-fit`/`auto-fill` 建立可伸缩轨道。

**边界与取舍**

Grid/Flex 子项的最小内容尺寸可能造成溢出；需要时在正确层级设置 `min-width: 0` 或合理的 `minmax(0, 1fr)`，不能盲目加 `overflow: hidden`。

**常见误区**

用绝对定位拼常规布局；把 Grid 当成性能优化本身。

## content-visibility 的性能与可访问性边界

**问题**

长文档能否用 content-visibility: auto 代替虚拟列表？

**核心答案**

content-visibility: auto 允许浏览器跳过视口外内容的布局与绘制，适合长页面的原生渐进优化；配合 contain-intrinsic-size 预留尺寸，降低滚动条抖动和布局偏移。它不减少 DOM 节点、内存、事件监听或数据处理，因此超大交互列表仍可能需要虚拟化。

**边界与取舍**

- auto 的离屏内容仍保留在 DOM 和可访问性树，可被查找和聚焦；不要把它当 display: none。
- hidden 与 auto 的可访问性语义不同。
- 必须实测布局稳定性、键盘导航、查找和浏览器兼容性。

**追问**

## 什么会触发布局抖动，如何用代码和性能面板定位？

**考察意图**

浏览器渲染路径、测量能力。

**核心答案**

DOM/CSS 改变后，几何相关属性可能引发布局，随后是绘制与合成。高频循环中交替写样式、读取 `offsetWidth`/`getBoundingClientRect()` 会迫使浏览器提前计算。先在 Performance 面板和 Layout Shift 标记中确认，再批量读取、集中写入；动画优先 `transform`/`opacity`，但仍要录制验证。

**边界与取舍**

不应只凭“某属性一定更快”下结论；阴影、滤镜、大图层和合成层数量也有代价。

**常见误区**

将所有元素加 `will-change`；把 CLS 仅理解为图片未设尺寸。

**追问**

如何区分脚本长任务、强制同步布局和网络瓶颈？

## 何时使用逻辑属性与 cqi ，如何处理 writing mode？

## 大型可筛选列表怎样减少无意义更新？

**考察意图**

将“优化”落到数据、组件和 DOM 三层。

**核心答案**

## 布局抖动来自交错读写

**核心答案**

同一任务中先改写影响布局的样式，再读取 `offsetWidth`、`getBoundingClientRect()` 等几何信息，会迫使浏览器提前同步布局。

循环内反复写→读会让布局重复发生；先批量读取，再批量写入，可减少强制同步布局。

**边界与取舍**

批处理不能消除业务必须的布局，只减少不必要的重复；DOM 规模和选择器仍影响成本。

**常见误区**

`requestAnimationFrame` 包住循环就自动消除抖动。

## 评审卡片何时用 Container Query 而不是 Media Query

**问题**

同一评审卡会出现在主页面、Drawer 和侧栏，如何决定响应式边界？

**考察意图**

组件封装、布局上下文、渐进增强和测试。

**核心答案**

视口级壳仍用 media query；卡片内部按可用容器宽度切换标题/操作/元信息布局时用 `container-type:inline-size` 和命名 container。默认样式先可用，再在 `@container` 增强；断点来自内容崩坏点而非设备型号。

**边界与取舍**

容器声明可能影响 sizing/formatting context；嵌套时明确查询哪个祖先。打印、缩放、长文本和本地化需单独验证。

**常见误区**

所有节点都设 container；只改列数不测溢出、焦点和读屏顺序。
