## AbortSignal 是协作式取消

**核心答案**

signal 传播取消意图，消费方必须监听并尽快停止可取消工作。

浏览器 fetch、Node 下游 fetch/任务共享信号或派生信号；取消按 AbortError 单独处理。

**边界与取舍**

超时事件或卸载本身不会自动回滚已提交的服务端副作用。

**常见误区**

组件卸载后请求和服务端计算自然停止。

## Context、外部 store 与请求缓存如何边界化？

**考察意图**

状态分层。

**核心答案**

## External store 的快照必须可比较且稳定

**核心答案**

`useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot?)` 把 React render 接到外部事实源。

store 通知后 React 重读 snapshot，并用 `Object.is` 与上次值比较；真正变化才触发对应更新。

**边界与取舍**

mutable store 也可接入，但必须缓存不可变 snapshot；SSR 时 server/client 初始 snapshot 必须一致。

**常见误区**

每次 `getSnapshot()` 返回 `{...state}` 更安全；实际会造成无意义更新甚至循环。

## Fetch 只在网络层失败时 reject

**核心答案**

HTTP 404/500 通常仍得到 fulfilled `Response`；`response.ok` 只在 200–299 为 true。

先检查状态/Content-Type，再按成功 DTO 或 problem details 解析；网络错误、超时/取消和 HTTP 错误分开建模。

**边界与取舍**

204 没有 JSON body；错误代理可能返回 HTML；成功状态也不能跳过运行时 schema。

**常见误区**

进入 `.then` 就表示业务请求成功。

## HTTP 缓存不等于 bfcache

**核心答案**

HTTP 缓存复用响应；bfcache 恢复页面快照。

HTTP 通过 freshness 与条件请求校验；bfcache 可恢复 JS/DOM 状态。

**边界与取舍**

后退导航可能不重新走 HTTP 校验。

**常见误区**

no-cache 等于不保存。

## HTTP 缓存的 freshness、validation 与 invalidation 有何区别？

**考察意图**

是否能分层解释“旧数据”。

**核心答案**

freshness 由 `max-age` 等决定缓存能否直接复用；过期后可带 `If-None-Match`/`If-Modified-Since` 做 validation，未变得到 `304` 并复用实体；invalidation 是应用/CDN 等主动使条目不再可用。HTTP 并没有一个让所有缓存强制删除的通用响应头。

**追问**

为什么变更后的页面仍可能看到旧数据？

**边界/误区**

不要把浏览器、CDN、Service Worker、框架数据缓存混成一个缓存；`304` 不是“没有网络请求”。

**来源/审校**

现代 JavaScript 教程、Front-End Checklist、MDN；**已准入**。

## HTTP 缓存：no-cache、no-store 与 immutable

**问题**

SPA 的 HTML、带 hash 静态资源和用户私有 API 应如何设置缓存？

**核心答案**

HTML 通常使用 no-cache 允许存储但复用前校验，确保能发现新资源入口；带内容 hash 的静态资源使用长 max-age + immutable；私有响应根据敏感性使用 private, no-cache，确实不应存储时才用 no-store。校验依靠 ETag/If-None-Match 或 Last-Modified/If-Modified-Since，未变化返回 304。

**边界与取舍**

- no-cache 不是“不缓存”，而是复用前校验。
- no-store 不会清除此前已经存储的响应，并会损失部分浏览器能力。
- bfcache 是页面快照恢复，不等同于 HTTP 缓存。

**追问**

CDN 的 s-maxage 与浏览器 max-age 如何配合？如何回滚错误的 immutable 资源？

## 为什么 SSR 中的副作用要格外谨慎？

**考察意图**

服务端请求隔离与资源生命周期。

**核心答案**

SSR 每个请求必须拥有隔离状态；服务端渲染期间不应启动长期轮询、浏览器 API 或无界 watcher。把数据获取放在框架约定的 SSR 数据层，并在请求结束释放资源；客户端 hydration 后再启动浏览器副作用。

**边界与取舍**

SSR/async `setup()` 的具体时序随框架集成不同，生产策略要以使用的 Vue/Nuxt 版本与回归测试为准。

**常见误区**

在模块顶层缓存每个用户的响应式 store。

**追问**

如何验证泄漏？——压测多请求、采样 heap、记录活跃 watcher/连接数并做请求结束断言。

## Service Worker 不能替代应用级一致性策略，为什么？

**考察意图**

区分资源缓存与领域数据。

**核心答案**

Service Worker 擅长拦截导航/静态资源与定义请求缓存策略，但不理解用户、租户、授权、写入顺序或业务冲突。应用仍要为 API 数据定义 cache key、失效、鉴权切换、加密/清除和 mutation outbox。

**边界与取舍**

cache-first 适合版本化静态资源；用户数据常需 network-first、stale-while-revalidate 或显式版本校验，且不能缓存带私密响应的共享 URL。

**常见误区**

“装了 SW 就天然离线可编辑”。

## Vue SSR 中副作用、单例和请求状态如何隔离？

**考察意图**

**核心答案**

## Cache-Control: no-cache 与 no-store 如何选？

**考察意图**

安全与性能取舍。

**核心答案**

`no-cache` 允许保存但每次复用前必须向源站验证，适合希望缓存协作但不能直接使用陈旧表示的 HTML/API；`no-store` 要求不存储，适合含高度敏感数据的响应。静态带内容哈希的资源通常用长 `max-age, immutable`，而 HTML 用较短 freshness/验证来指向新资源。

**追问**

**边界/误区**

`no-cache` 不等于“不缓存”；`no-store` 也不能替代 HTTPS、鉴权和服务端的敏感数据最小化。

**来源/审校**

Checklist、Interview Handbook、MDN；**已修订**，补充安全边界。

## bfcache 恢复为何会出现陈旧 UI，怎么处理？

**考察意图**

是否知道 back/forward 可能恢复整页内存，而非重新加载。

**核心答案**

bfcache 命中后，DOM 与 JS 堆可从冻结态恢复，组件“重新挂载”假设失效，时间敏感数据、会话和连接状态可能过期。监听 `pageshow`，当 `event.persisted` 为真时按资源版本/TTL 轻量校验并按需失效；恢复可见性、计时器、连接与表单草稿必须各有策略。指标区分 normal load、bfcache restore、restore 后 revalidate。

**边界与取舍**

不要强制禁用 bfcache 来换取“总是刷新”；金融/权限等高风险界面可在恢复时重新授权或重新校验。**误区：** `pageshow` 就等于网络已刷新。**追问：** 多标签登出后返回旧标签怎样收敛？

## SPA 如何同时支持刷新、前进后退和直达 URL？

**考察意图**

能否定义路由的唯一事实来源。

**核心答案**

## pushState 、 replaceState 与 popstate 的职责？

**考察意图**

区分“写历史”“激活历史”“渲染页面”。

**核心答案**

`pushState(state, '', url)` 增加当前同源历史条目，`replaceState` 原地替换当前条目；二者不会触发 `popstate`。用户前进/后退或 `history.go()` 激活另一条目才触发 `popstate`，路由器据其 `event.state` 与 URL 渲染。首个条目需在初始化时 `replaceState`，否则返回首屏没有状态。

**边界与取舍**

state 只放小型、可序列化 UI 线索，敏感数据不进 URL/state；直达 URL 与刷新必须可由服务器或客户端路由恢复。**误区：** 把 `popstate` 当成路由跳转的唯一回调。**追问：** 为什么要避免把响应实体塞入每个 history state？

来源：现代 JavaScript 教程（curated）；[MDN History API](https://developer.mozilla.org/en-US/docs/Web/API/History_API/Working_with_the_History_API)（primary）。审校：**已准入**，current。

## Pointer Events 拖动如何处理 capture、cancel 与滚动

**问题**

**考察意图**

浏览器事件模型、手势竞争和资源清理。

**核心答案**

pointerdown 记录唯一 pointerId、按需 capture；只处理该 ID 的 move；up/cancel/lostpointercapture 走同一幂等 cleanup。用 `touch-action` 声明允许的原生滚动轴，不靠全局 preventDefault；组件卸载也释放 rAF/监听状态。

**常见误区**

**追问**

## watch 的 flush 何时影响 DOM 读取？

**考察意图**

理解批处理更新与副作用调度。

**核心答案**

默认 `flush: 'pre'` 在组件更新前执行；需要读取本组件已更新 DOM 时用 `flush: 'post'`；`sync` 不批处理，只用于极小、同步的状态协调，不能放高频数组变更。

**边界与取舍**

`post` 不等于浏览器已绘制；若需要下一帧的布局/绘制时机，仍需结合 `requestAnimationFrame` 并测量。

**常见误区**

把 `sync` 当“更及时、更好”。

**追问**

为什么 `nextTick` 不能替代所有 post watcher？——它等待本轮 DOM 更新，但不表达依赖监听和清理语义。

## 可控时间不等于清空所有异步任务

**核心答案**

fake timers 接管选定的计时 API；Promise/Vue 更新队列、网络回包和浏览器渲染可能属于其他队列。

明确推进 timer，再等待相关 Promise/框架更新；测试结束恢复真实时钟和 Mock。

**边界与取舍**

Vitest 默认不会自动 fake `nextTick`/`queueMicrotask`；Vue `nextTick` 只等待 Vue DOM flush，外部 Promise 用 `flushPromises`。

**常见误区**

`runAllTimers()` 后所有异步副作用必然结束。

## 浏览器渲染不是固定每次全流程

**核心答案**

样式计算、布局、绘制、合成是理解成本的模型，不表示每次更新都必然执行全部阶段。

几何变化通常触发布局，视觉变化可能绘制，合成层上的变换可能只需合成；最终路径由浏览器、属性和页面状态决定。

**边界与取舍**

创建合成层也有内存、上传和栅格化成本，必须用 trace 验证。

**常见误区**

改 `transform` 就一定由 GPU 完成且绝不会 repaint。

**常见误区**
