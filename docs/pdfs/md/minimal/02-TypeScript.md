# 运行时契约与校验

- **API 响应缩窄应放在哪里？** 机制/边界；在请求边界完成运行时解析和类型收窄，内部模块只接收已验证领域类型。 取舍：全量 schema 更安全但有成本，可按风险选择轻量 guard。（坑：每个组件自行判断字段。）
- **Schema 约束｜状态与接口契约** 在“问卷 Schema、动态卡片与后端变更同步”中，先明确状态所有者与契约，再落实：模型或接口输出须通过运行时 schema 校验，类型只覆盖编译期。（坑：TypeScript 类型能拦住运行时脏数据。）
- **TypeScript 如何写可演进的事件契约？** 判别联合让消费者穷尽处理；新增字段可选、未知 type 记录并安全忽略或触发升级；边界处以 Zod/JSON Schema 等运行时校验。（坑：相信 TypeScript 会验证 WebSock…）
- **satisfies 与 as 有何不同？** 机制/边界；satisfies 检查兼容性且保留表达式推断；as 告诉编译器按目标类型看待，可能掩盖错误。 取舍：二者都不产生运行时校验。（坑：用 as 修复所有报错。）
- **satisfies 能做什么、不能做什么** satisfies 在编译期检查表达式与目标类型兼容，同时保留表达式更具体的推断，适合 route/action/config 表；它不产生运行时检查…（坑：把 satisfies 当 schema vali…）
- **自定义字段｜项目落地** 在“Skill Market、知识关联与自定义字段”中，先明确状态所有者与契约，再落实：字段 schema 需包含 key、类型、校验、默认值与迁移。（坑：JSON 任意扩展无需版本。）
- **语义模型｜项目落地** 在“泳道图接口、预览取舍与索引基线”中，先明确状态所有者与契约，再落实：保存 DrawIO XML 时应同步可验证的语义模型并保留原始 XML。（坑：XML 能打开就无需结构化数据。）

- **运行时 schema 如何处理版本漂移与 coercion** 按方向区分：读取响应通常允许未知新增字段但严格校验已消费字段；写请求使用 allowlist，拒绝未授权字段；coercion 只对明确、可逆、无歧义值开放…（坑：开启 coercion 能自动修复所有后端不一致。）
