# 提交与历史

- **CI 中如何处理 flaky test 而不掩盖缺陷** 单独标为 flaky，保留首败与重试的 trace、seed、run、浏览器和提交；先复现并定位共享状态、未等待异步、时间/网络依赖。（坑：提高 timeout、无限重试、删掉偶发测试。）
- **React Compiler 如何灰度并证明收益** 先修 Rules of React；按目录/annotation 小范围启用；单独提交配置与代码修正；建立行为回归…（坑：构建成功或 render 次数下降就等于用户体验提…）
- **Release 分支如何回退有依赖的多提交改动** 先画提交/功能依赖并确认已合并拓扑；能关 flag 先隔离；代码按逆依赖顺序 revert，merge commit 明确 mainline…（坑：直接 reset/force-push…）
- **Revert 是追加反向提交而非抹除历史** git revert 根据既有提交生成反向变化并创建新提交，适合已共享历史。先识别目标及后续依赖，必要时按逆依赖顺序回退；冲突解决后重新跑门禁。（坑：revert 等价 reset…）
- **cherry-pick 最小提交的前提？** 机制/边界；提交必须尽量自洽，先检查依赖顺序与工作树，冲突后验证 index/内容并运行最窄检查。 取舍：跨分支回放会产生新提交 ID；公开回溯可用 -x。（坑：按日期盲选一串提交。）
- **交互性能优化如何提交、发布与回滚** 先保留可复现基线；将测量埋点、行为修复、纯样式优化按可审查边界提交，CI 跑功能/无障碍/性能预算；按版本灰度，比较相同人群的 INP p75、长任务…（坑：代码行数减少或构建通过就是性能收益。）
- **分支指针｜状态与接口契约** 在“Git 分支、变基与冲突延伸”中，先明确状态所有者与契约，再落实：Git 分支是指向提交的可移动引用，工作区和暂存区是不同状态。（坑：分支是完整代码副本。）

# 审查与 diff

- **Git bisect 如何在测试不稳定时产出可信回归证据** 固定环境、数据和入口，先让判定脚本在已知 good/bad 多次稳定；bisect 每点运行同一 oracle，对不可构建或不确定提交用 skip…（坑：构建失败一律 bad；bisect 找到的提交自动…）
- **如何从大 diff 中排除格式化噪声？** 机制/边界；先看 stat/文件范围，再用 ignore-space 作为辅助，最终回到真实 patch 与行为验证；不要让噪声掩盖语义。（坑：只看 --stat 就审完。）
- **版本对比｜性能安全取舍** 在“完成卡、版本对比回滚与导入”中，先明确状态所有者与契约，再落实：版本 diff 需基于不可变快照、稳定序列化和明确比较基线。（坑：直接 diff Markdown 永远准确。）
