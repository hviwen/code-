## React Compiler 如何灰度并证明收益

**问题**

大型存量项目怎样引入 React Compiler，而不是全量打开后凭感觉验收？

**考察意图**

Git、工程化、性能与回滚。

**核心答案**

先修 Rules of React；按目录/annotation 小范围启用；单独提交配置与代码修正；建立行为回归、Profiler/真实用户指标和 bundle/build 指标；feature gate/A-B 灰度，异常可快速关停。

**边界与取舍**

Compiler 自动 memoization 不保证每个页面更快；第三方库和手写 memo 需逐步核查，不能盲删。

**常见误区**

构建成功或 render 次数下降就等于用户体验提升。

**追问**

怎样区分编译器收益与同时发生的业务改动？

**快答**

小范围启用、独立提交、行为与性能双门禁、A/B/gating、可快速回滚。

## 交互修复如何随 release merge 做回归与回滚

**问题**

数据看板、拖动、逾期提示在同一 release 合并，如何降低回归定位成本？

**考察意图**

Git 提交边界、测试矩阵、灰度与回滚。

**核心答案**

保留功能提交与修复提交的语义边界；CI 绑定单测、键盘/触摸组件测试、关键 E2E 和性能预算；合并前记录 base/head、依赖和 feature flag。线上按功能标记监控错误/INP，问题用可定位 revert/flag 回退，避免手工混合复制。

**边界与取舍**

merge commit 保留集成历史，rebase/cherry-pick 改变拓扑；选择服从团队流程，回滚前核依赖提交。

**常见误区**

release merge 后只看构建，或一次 revert 不检查后续依赖。

**追问**

如何用 bisect 区分数据看板与全局样式 token 回归？
